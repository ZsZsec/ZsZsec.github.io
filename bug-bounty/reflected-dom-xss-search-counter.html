Reflected DOM XSS_

CWE-79Medium
Web SecurityDOM XSSReflected XSSJavaScript

Encontré este comportamiento durante pruebas autorizadas en un programa privado de bug bounty. La página pública de búsqueda leía el término desde los parámetros search o q y, después de cargar, lo insertaba en el contador de resultados mediante innerHTML.

El frontend intentaba limpiar el valor antes de renderizarlo, pero lo hacía con expresiones regulares. Las etiquetas completas se eliminaban; una etiqueta sin > sobrevivía al filtro y el parser del navegador la completaba al procesar el HTML final. Eso permitía ejecutar JavaScript en el origen de la aplicación al abrir un enlace preparado.

El programa, el dominio, el identificador del reporte, la versión, las rutas internas y los nombres propios están omitidos o sustituidos por valores sintéticos.

Del parámetro al DOM

El módulo de búsqueda obtenía el término directamente de la URL:

const params = new URLSearchParams(window.location.search);
const term = params.get("search") || params.get("q") || "";

Más adelante construía el contador de resultados como una cadena HTML:

counter.innerHTML = term.trim()
  ? `<strong>${count}</strong> ${label} ${foundFor} <strong>${term.trim()}</strong>`
  : `<strong>${count}</strong> ${label} ${found}`;

El valor controlado terminaba dentro de innerHTML. La seguridad de ese flujo dependía por completo de la limpieza aplicada antes del sink.

La sanitización parcial

El bundle eliminaba primero patrones con forma de etiqueta y después aplicaba una denylist:

function cleanTerm(value) {
  return removeRiskyTags(value.replace(/(<([^>]+)>)/gi, "")).trim();
}

function removeRiskyTags(value) {
  const blocked = "script|style|iframe|object|embed|form|input|button";
  const pattern = new RegExp(`</?(${blocked})(\\s[^>]*)>`, "gi");
  return value ? value.replace(pattern, "") : "";
}

Ese enfoque tenía tres problemas:

  1. El primer regex solo eliminaba patrones que ya contenían >.
  2. La denylist no cubría todos los elementos con capacidad de ejecutar eventos.
  3. El valor resultante seguía llegando a un sink HTML.

La diferencia que confirmó el bypass

Primero probé una etiqueta completa:

procurement <b>ZZ</b>

La página mostró procurement ZZ como texto y no creó un nodo nuevo. Después retiré el > de una etiqueta con un manejador de evento:

procurement <img id=xss-probe src=x onerror=alert(1)//

Esta segunda entrada no coincidía con el regex de eliminación. Cuando el frontend la concatenaba con el cierre </strong> de la plantilla, el parser del navegador utilizaba el siguiente > disponible para completar la etiqueta inyectada.

El flujo completo era:

search / q
    ↓
URLSearchParams
    ↓
regex que requiere un > ya presente
    ↓
innerHTML con cierre </strong>
    ↓
el navegador completa <img ...>
    ↓
ejecución de onerror

Reproducción anonimizada

Utilicé una URL con esta estructura:

https://search.example.test/search?search=procurement%20%3Cimg%20id%3Dxss-probe%20src%3Dx%20onerror%3Dalert(1)%2F%2F

Al abrirla, el recurso inexistente disparó onerror y apareció el alert(1). La misma ruta vulnerable también era alcanzable mediante el parámetro q.

El DOM resultante seguía este patrón:

<span id="result-count">
  <strong>42</strong> results found for
  <strong>procurement <img id="xss-probe" src="x" onerror="alert(1)//</strong"></strong>
</span>

La respuesta inicial del servidor mantenía el término escapado dentro de la configuración de arranque. La ejecución aparecía después, cuando el JavaScript del cliente recuperaba la URL y reconstruía el contador. Por eso lo clasifiqué como DOM XSS y no como reflexión HTML directa desde el servidor.

Impacto

Una persona podía preparar un enlace que ejecutara JavaScript bajo el origen de la aplicación cuando otra persona lo abriera. La página era pública y no requería autenticación para reproducir el comportamiento.

No atribuí acceso adicional que no hubiera comprobado. El impacto posterior dependería de los datos y acciones disponibles para la víctima dentro de ese origen.

Remediación

El término de búsqueda debe tratarse como texto, no como HTML. Si el formato del contador es fijo, los elementos pueden crearse por separado y el valor controlado asignarse con textContent:

const termNode = document.createElement("strong");
termNode.textContent = term;
counter.replaceChildren(prefixNode, termNode);

La corrección no debería depender de otro regex o de ampliar la denylist. Como defensa adicional, una CSP sin unsafe-inline reduciría la ejecución de manejadores inline, pero no sustituye la eliminación del sink inseguro.

Estado del reporte

El reporte fue enviado al programa y permanece pendiente de revisión.
