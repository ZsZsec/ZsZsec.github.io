Encontré esta vulnerabilidad durante pruebas autorizadas dentro del programa de divulgación de vulnerabilidades de NASA. La aplicación tomaba un parámetro de la URL, aplicaba un encoder para HTML y después enviaba el resultado a un decoder JSON heredado que utilizaba eval().

El valor nunca llegaba a un sink HTML. El JavaScript se ejecutaba porque la aplicación trataba una cadena controlada desde la URL como código.

El sistema concreto se mantiene anónimo. El dominio, la ruta, el parámetro y los nombres internos utilizados en los ejemplos son sintéticos.

El flujo vulnerable

La aplicación utilizaba una versión heredada de ExtJS con el parser JSON nativo deshabilitado. En esa configuración, el framework recurría a un decoder basado en eval().

El flujo podía resumirse así:

parámetro de la URL
        ↓
Ext.String.htmlEncode()
        ↓
estado inicial de la aplicación
        ↓
decoder JSON heredado
        ↓
eval("(" + input + ")")

El uso de htmlEncode() daba la impresión de que la entrada estaba sanitizada. Sin embargo, ese método solamente protegía caracteres relevantes para HTML, como <, >, comillas y &.

El sink era JavaScript. Caracteres como paréntesis, puntos y corchetes seguían intactos, por lo que una expresión válida podía atravesar el encoder y llegar hasta eval().

Por qué el encoder no servía

La entrada se estaba protegiendo para un contexto diferente al que finalmente la interpretaba:

contexto protegido: HTML
contexto real:      JavaScript

Un payload como el siguiente no necesita etiquetas HTML ni comillas:

alert(document.domain)

Al llegar al decoder, la operación efectiva era equivalente a:

eval("(" + "alert(document.domain)" + ")")

El navegador evaluaba primero alert(document.domain) y mostraba el origen de la aplicación.

Reproducción

Para el artículo reemplacé la URL original por un dominio reservado y cambié el nombre del parámetro:

https://search.example-space.test/app/?state=alert(document.domain)

La solicitud equivalente era:

GET /app/?state=alert(document.domain) HTTP/1.1
Host: search.example-space.test
Accept: text/html
Connection: close

Al abrir el enlace, la aplicación leía state durante la carga inicial. El valor pasaba por el encoder HTML, llegaba al decoder y terminaba ejecutándose en el origen de la aplicación.

No era necesario modificar headers, utilizar un navegador antiguo ni preparar una interacción adicional dentro de la página.

Impacto

La ejecución ocurría bajo el mismo origen de la aplicación. Si una víctima abría el enlace mientras mantenía una sesión activa, el script podía interactuar con cualquier recurso disponible para esa sesión.

Esto permitía, dentro de las capacidades del origen:

  • Leer información renderizada en el DOM.
  • Realizar solicitudes autenticadas desde el navegador de la víctima.
  • Modificar el contenido visible de la aplicación.
  • Insertar formularios o interfaces falsas.
  • Redirigir la navegación hacia otro sitio.

El hecho de que el enlace perteneciera a un dominio legítimo aumentaba su utilidad en escenarios de phishing. Las políticas CSP presentes no restringían la ejecución de scripts, por lo que no impedían esta cadena.

Causa raíz

El problema tenía dos partes:

  1. Un valor controlado desde la URL alcanzaba un decoder implementado con eval().
  2. La aplicación aplicaba encoding para HTML aunque la entrada iba a utilizarse en un contexto JavaScript.

Eliminar solamente el encoder no solucionaba el problema. El sink peligroso seguía siendo el decoder capaz de ejecutar código.

Remediación

La corrección principal era habilitar el parser JSON nativo y retirar cualquier ruta de decodificación basada en eval().

También era necesario:

  1. Parsear los datos con JSON.parse().
  2. Rechazar entradas que no cumplieran el esquema esperado.
  3. Evitar que parámetros arbitrarios de la URL se utilizaran como estado ejecutable.
  4. Aplicar controles según el contexto real del sink.
  5. Utilizar una CSP restrictiva como defensa adicional, no como sustituto del fix.

Resultado

Reporté el hallazgo en junio de 2026. NASA respondió y el reporte fue cerrado como corregido en julio de 2026. Al repetir la prueba, el payload ya no se ejecutaba.

El hallazgo fue reconocido mediante una Letter of Recognition.
